## 快速開始

```bash
npm install
npm start
```

啟動後終端機會印出三個位址與一組主辦端通行密鑰：

- **大螢幕**　`http://localhost:3000/screen/` — 投影用
- **手機控制器**　`http://<區網IP>:3000/controller/` — 手機須與電腦連同一個 Wi-Fi
- **主辦端控制台**　`http://localhost:3000/host/` — 需輸入終端機顯示的 6 碼密鑰

現場部署時，把區網位址做成 QR Code 給參與者掃描即可。HTTP 與 WebSocket 共用同一個
連接埠，手機端由 `location.host` 自動推導伺服器位址，無須任何設定。

> 主辦端密鑰每次啟動重新產生。控制台握有踢人與結算全場的能力，
> 而現場所有人連在同一個區網、路徑可被掃出，因此不能只靠網址保密。

## 跑一次完整流程

1. 開大螢幕 `/screen/`
2. 用兩支手機（或兩個瀏覽器分頁）開 `/controller/`，各自命名與捏臉進場
3. 開 `/host/`，輸入密鑰，發布「找一個人配對」任務
4. 手機上會出現任務橫幅與自己的 4 位配對碼
5. 在 A 手機輸入 B 的配對碼 → B 手機跳出確認 → 按下確認
6. 大螢幕浮現完成提示，兩個角色各自擴散一圈綠環；主辦端的社交連結數 +1
7. 在主辦端打一題即時問答（題目、選項、點圓圈標正解、選作答時間），按「出題」
8. 手機自動跳出題目；按下選項後鎖定，大螢幕顯示倒數與作答人數
9. 時間到自動公布正解（也可按「提前公布答案」），答對者得分並在場上擴散光環
10. 右下角排行榜即時更新；按「收題」即可出下一題

執行測試：

```bash
npm test              # 單元測試（155 項，約 5 秒）
npm run test:e2e      # 端對端測試（76 項，會自行啟動伺服器並重開一次，約 70 秒）
npm run preview:scene # 產生 docs/scene-preview.svg，不必開瀏覽器就能看場景
```

## 資料保存

**刷新頁面不會掉資料。** 手機把 userId 與重連憑證存在 `localStorage`，
大螢幕與主辦端重連後由伺服器補送當下的完整現況：

| 情況 | 行為 |
| --- | --- |
| 手機／大螢幕／主辦端重新整理 | 全部接得回來，積分與進行中的題目照舊 |
| 手機關掉超過 45 秒 | 角色被回收，但重新進場時仍可用原憑證認領回來 |
| 主動按「離開」或被主辦端移除 | 憑證作廢，之後重新進場是全新角色（設計如此） |
| **伺服器重開或當掉** | 積分、社交圖譜、任務與問答紀錄都還在，通行密鑰不變 |

**存的是資料，不是即時狀態。** 快照寫在 `data/state.json`：積分帳本、社交圖譜、
任務與問答紀錄、以及身分目錄。角色的座標、速度、α 權重一律不存 ——
它們每秒變動 30 次，重算即可，寫進檔案只會讓每次落地都變成整份重寫。
啟動當下先寫一次（讓通行密鑰立刻落地），之後每 5 秒存一次（有變動才寫），
按 Ctrl+C 正常關閉時再強制寫一次。因此最壞情況 —— 強制結束行程或斷電 ——
也只會退回最多 5 秒前的狀態。

寫入採「先寫暫存檔再原子改名」。直接覆寫原檔的話，寫到一半斷電會留下語法壞掉的
JSON，那比沒有檔案更糟 —— 下次啟動載入失敗，而現場沒有人有空去修一個 JSON。
（真的壞掉時系統仍會照常啟動，壞檔改名成 `.bad` 留著事後查。）

**積分為什麼跟得回來。** 分數掛在 `userId` 上，而 `userId` 在伺服器重開後會消失，
所以身分目錄要落地：手機帶著 `localStorage` 裡的 userId 與憑證回來時，
伺服器以原本的 id 重建角色，積分、社交關係、任務進度自然全部接回。
憑證比對用定時安全比較，不符者拿不到別人的角色。

**主辦端用同一組密鑰登入。** 密鑰取用順序為
環境變數 → 快照裡的舊密鑰 → 重新產生。要固定成自己指定的號碼：

```bash
PERSONAFLOW_HOST_KEY=ABC123 npm start     # 6 碼，英數
```

不指定時，只要 `data/state.json` 還在，重開後就會沿用上一次的密鑰 ——
伺服器重開通常正好是現場最忙亂的時刻，這時再叫主辦者重讀一組新號碼並不合理。

> ⚠ `data/` 內含重連憑證與主辦端密鑰的明文。這是區網單機活動的合理取捨
> （拿得到這個檔案的人本來就拿得到整台伺服器），但別把它放進版本控制或雲端同步。
> 換一場新活動要清空資料時，直接刪掉 `data/state.json` 即可。

其他環境變數：`PERSONAFLOW_STATE_FILE` 指定快照路徑，
`PERSONAFLOW_PERSIST=0` 完全關閉落地（測試用，現場請勿設定）。

## 積分與問答的三個關鍵決定

**積分帳本獨立於任何玩法。** 配對、任務達標、答對問答都只是呼叫
`scores.award()` 的得分來源，帳本本身不知道它們是什麼。分數要跨玩法累計，
若把它塞進 `missions.js`，問答就得自己再存一份，之後每一個要顯示總分的地方
（排行榜、大螢幕、主辦端、匯出）都得各自合併兩份資料。日後再加新玩法，
只要多呼叫一次 `award()`。

**正解在揭曉前絕不離開伺服器。** 送給手機與大螢幕的是 `publicView()`，
它不含 `correctIndex`，作答人數也不含分佈 —— 倒數期間洩漏分佈等於洩漏答案。
判分完全在伺服器端進行；把整題送出去再由前端比對，現場任何一位會開
開發者工具的同學都能拿滿分。

**時間到由主迴圈推進，不用 `setTimeout`。** 定時器在事件迴圈被拖慢時會延後觸發，
而截止時間必須與大螢幕上的倒數一致；主迴圈本來就對齊絕對截止時間
（見 `scheduler.js`）。倒數則以「剩餘毫秒」下發而非絕對時戳 ——
現場一定有人的手機時鐘不準，用時戳倒數會出現一進來就剩負秒數。
另有 700ms 的遲到寬限：封包要走現場的無線網路，沒有寬限的話，
「按下去時還剩 0.2 秒」會被判成沒作答，而寬限內的作答仍以完整時長計速度分。

## M3 的兩個關鍵實作決定

**靜態場景只渲染一次。** rough.js 每次呼叫都會重新產生隨機化路徑，逐幀重繪除了慢，
畫面還會「沸騰」—— 手繪抖動每幀都變，觀感會變成雜訊而非手繪。
因此場景離屏渲染一次後每幀貼圖，只有角色需要逐幀重算。

**步態改用時間基準。** 技術文件的公式以 `frameCount` 為自變數（ω = 0.2 rad/frame），
但這會讓動畫速度隨螢幕更新率改變 —— 同一個角色在 60Hz 與 144Hz 的投影機上
步頻不同。實作全部改為時間基準，並以 60fps 換算出等價常數，維持文件指定的觀感。

**技術選型偏離：**技術文件寫 `p5.js + rough.js`，實作使用 `Canvas2D + rough.js`。
rough.js 本來就直接操作 Canvas2D context、不需要 p5；而渲染管線（座標映射、
內插、Y 軸排序）已為本專案寫好，改用 p5 需要重寫且多引入約 1MB。

> e2e 腳本刻意不放在 `test/`。Node 的測試探索會把 `test/` 底下任何 `.mjs`
> 都當成單元測試檔，放進去會讓每次 `npm test` 都啟動一次伺服器。

## 效能實測（30 個角色）

| 指標 | 實測值 | 備註 |
| --- | --- | --- |
| 模擬 tick 成本 | p50 0.011ms / p99 0.064ms | 佔 33.33ms 預算的 0.03% |
| 實際模擬頻率 | 30.0 Hz | 改用 `scheduler.js` 前為 27.3 Hz |
| STAGE_SYNC 頻寬 | 127 KB/s 每台大螢幕 | 4,330 B/幀 |
| 管線延遲 | p50 18.1ms / p99 49.3ms | localhost，不含 Wi-Fi 與手機端節流 |

CPU 餘裕極大，瓶頸不在運算。若日後要降低延遲，直接提高 `TICK_HZ` 是可行的
（60 Hz 時頻寬約 254 KB/s，區網仍充裕）。

## 連線防護

以下四項為 1.0 版實測發現並已修正的問題，`test/hardening.test.mjs` 有對應測試防止回歸：

| 問題 | 修正 |
| --- | --- |
| 任何人可冒用他人 `userId` 接管其角色 | 登入時下發 `rejoinToken`，重連須以定時安全比較驗證 |
| 入站訊息無速率限制（實測可達 29,000/秒） | Token Bucket：容量 60、每秒補充 60，持續逾量即斷線 |
| 重複 `CLIENT_JOIN` 造成永久幽靈角色洩漏 | 一條連線只綁定一個角色；重複送出僅更新暱稱與造型 |
| 場域人數無上限 | `MAX_AGENTS = 120`，額滿時回傳 `CLIENT_REJECT` |

速率限制的容量刻意設為協定規格（20 Hz）的 3 倍。手機自背景喚醒或現場 Wi-Fi
壅塞恢復時，排隊訊息會一次湧入，那是正常行為，不應被誤判為攻擊。

## 給接手 M3 的人

`public/screen/` 目前是為了驗證 M2 而寫的最小診斷畫布，**不是** M3。M3 開工時整個
目錄都會被 p5.js + rough.js 的實作取代，伺服器端無須任何更動 —— 大螢幕只需要：

1. 連線後送出 `SCREEN_HELLO`
2. 收 `STAGE_ROSTER` 取得每個人的捏臉設定（僅在有人加入／離開時送出）
3. 收 `STAGE_SYNC` 取得每幀的座標與狀態（30 FPS）

`STAGE_SYNC` 的每個角色帶有 M3 需要的全部渲染提示：

| 欄位 | 用途 |
| --- | --- |
| `x` `y` | 邏輯座標（場域為 1920×1080，需自行縮放到投影解析度） |
| `vx` `vy` | M2 合成後的最終速度向量 |
| `state` | `WALK` / `IDLE` — 決定是否播放彈跳步態（IDLE 完全靜止）|
| `facing` | `1` / `-1` — 轉向鏡像的 ScaleX |
| `mode` | `ACTIVE` / `SWARM` — 主動控制態或湧現漫遊態 |
| `alpha` | 0–1 的控制權重，可用於視覺上區分兩種狀態的強度 |
| `offline` | 是否顯示暫時離線符號 |
| `emote` | `CHEERS` / `HEART` / `WAVE` / `null` — 頭頂氣泡 |

## 手機端個人視角（CLIENT_SYNC）

手機控制器除了送出搖桿輸入，也會收到自己的座標與鄰居，用於
`public/controller/avatarRenderer.js` 的個人視角畫布。

| | STAGE_SYNC | CLIENT_SYNC |
| --- | --- | --- |
| 對象 | 大螢幕（廣播） | 每支手機（一對一） |
| 頻率 | 30 Hz | 10 Hz |
| 內容 | 全場所有角色 | 自己 + 半徑 320 內的鄰居 |
| 鄰居座標 | 絕對 | **相對於自己** |

頻率刻意低於大螢幕：大螢幕只有一條連線，手機則是每人一條，
30 Hz × 10 人會與貼圖搶現場無線頻寬。10 Hz 配合手機端內插，肉眼無差別。

鄰居座標在伺服器端就換算成相對值 —— 手機把自己畫在畫面中央，
需要的本來就是相對位移，也讓手機端不必知道場域原點。

**兩個容易改壞的地方**：

1. `CLIENT_SYNC` 的推送必須放在主迴圈 `screens.size === 0` 早退**之前**。
   放在後面的話，大螢幕沒接上時所有手機畫面會整個凍結 ——
   而「先開手機、投影機還沒接」正是佈場時最常見的狀態。
2. 節流比較要帶半個 tick 的容差（`>= CLIENT_SYNC_MS - TICK_MS / 2`）。
   主迴圈是 30 Hz（33.3 ms），嚴格的 `>= 100` 會讓第 3 個 tick 差 0.1 ms 被擋下，
   實際變成每 4 個 tick 送一次 —— 7.5 Hz 而非 10 Hz。端對端測試有頻率回歸防護。

手機端**不自行模擬位置**，這是與 issue #8（投影牆跑自己的 Boids）刻意相反的
選擇：本地模擬會讓使用者低頭看到自己穿牆、抬頭卻看見角色卡在牆邊。
伺服器狀態過期（掉封包或斷線）時畫面收斂到靜止，而不是以最後速度外推。

## 給接手素材的人

`shared/avatars.js` 內的 SVG 是風格對齊的**手繪佔位素材**。要換成官方 Open Peeps
向量資產時，只需替換各 part 的 `svg` 字串，組裝邏輯與驗證器都無須更動。

顏色一律比對調色盤白名單而非 hex regex —— 顏色會被字串插值進 SVG markup，
白名單能從根本消除注入風險。新增顏色請加進 `SKIN_TONES` / `ACCENT_COLORS`。
