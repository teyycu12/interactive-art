PersonaFlow 任務驅動架構

把系統從「再現現場」轉為「介入現場」。大螢幕不再只是反映參與者已經在做的事， 而是由主辦端發布任務、指定現場該發生什麼——破冰的因果機制第一次被寫進系統裡。

版本 v3.0 基準 技術文件 v2.0 狀態 待團隊確認 實作進度 M1 · M2 · Gateway 已完成

00改版摘要

v2.0 的四層架構與 M1、M2 全部保留，改動集中在系統的目的與 M4 的定位。

01為什麼要改

v2.0 宣稱達成實體破冰，但破冰的因果機制是缺的。

v2.0 的系統做的是再現：參與者移動搖桿，大螢幕顯示對應的角色移動。 這建立了共享的視覺場域，但它反映的是現場已經發生的事。兩個陌生人的角色在畫面上靠近， 不會讓這兩個人開口說話。

WP-D 的論述架構以「達成實體破冰」為核心主張，但 v2.0 並未提供任何促使陌生人互動的機制。 論述與系統之間有一個缺口。

v3.0 把因果方向反過來。系統轉為介入：主辦端發布任務，大螢幕指定現場該發生什麼， 參與者為了完成任務必須在物理空間中行動與交談。數位層對實體行為產生因果力， 而不只是映射——這正是混合空間論述（de Souza e Silva, 2006）真正有力的地方， 也讓 WP-D 的主張第一次有對應的系統機制可以指稱。

給 R4 的論述提示

三大理論支撐不需推翻，但重心要調整。Goffman 的自我呈現仍對應捏臉模組； Halbwachs 的集體記憶符號化改由「任務完成的累積記錄」承載，而非單一張合照； 社會臨場感與混合空間則從輔助論述升為主論述，因為它現在有了可驗證的行為機制。

存取控制

主辦端控制台必須與參與者端有實質區隔，不能只靠「網址沒人知道」。 現場所有人都連在同一個區網，路徑可被掃出。控制台需要獨立的通行密鑰， 於伺服器啟動時產生並印在終端機，主辦者手動輸入一次。

03任務系統

共用一套生命週期，驗證策略可插拔。三種任務類型的驗證模型差異極大，不可當成同一種東西實作。

3.1　任務生命週期

01發布 主辦端選定任務類型與參數，推送至全體手機與大螢幕
02執行 參與者在物理空間中行動；大螢幕持續顯示任務內容與完成人數
03提交 參與者提交完成憑據，形式依任務類型而異
04驗證 依該類型的驗證策略判定，自動或由主辦端裁決
05回饋 大螢幕即時呈現完成事件，這是任務回推現實的關鍵環節
06結算 主辦端關閉任務，記錄寫入行為 Log
設計原則

第 05 步不可省略。若任務完成後只有手機上跳出一行字，這就退化成一個手機小遊戲， 與專案要打破個人螢幕封閉性的核心命題背道而馳。每一次完成都必須在共享畫布上被看見。

排序依據是本專案的目標：回推現實交流。配對任務是三者中唯一強制產生物理互動的， 且不觸及任何部署阻擋，因此列為 v1 唯一範圍。另兩種延後的原因見 §09。

3.3　v1 規格：配對任務

關鍵洞察是驗證不需要照片。真正的完成證據是雙方的相互確認， 照片只是副產品。因此 v1 可以完全不碰相機。

  1. 每位參與者的手機上顯示一組 4 碼配對碼，每 60 秒輪換一次。
  2. A 走向 B，口頭索取並輸入 B 的配對碼。
  3. 伺服器建立待確認配對，推送確認請求至 B 的手機。
  4. B 按下確認，配對成立。逾 30 秒未確認則作廢。
  5. 大螢幕出現完成回饋，雙方任務進度更新，社交圖譜寫入一條邊。

要拿到對方的碼必須走過去開口問他——這個索取動作本身就是破冰， 而不是系統事後對破冰的記錄。

防繞過

隔空喊碼或在群組貼碼可以繞過物理接近。60 秒輪換是最廉價的對策，讓遠端分享不實用。 校內活動不需做到滴水不漏；若日後要強化，可考慮限制同一對參與者只能配對一次， 並要求配對雙方的角色在大螢幕上距離足夠近（利用既有的空間狀態矩陣）。

04社交圖譜

配對任務的累積產物。這可能比任務系統本身更有價值。

v2.0 規劃 M4 的構圖演算法要「依據社交圖譜將互相按讚互動的角色分群靠攏」， 但「按讚」是很薄的關係資料——兩人互點一下不代表任何實質互動。 配對任務每完成一次，就產生一條經雙方確認的真實社交連結： 這兩個人確實在物理空間中碰過面、講過話。一場活動下來累積出來的，是一張有效度的社交圖譜。

4.1　資料模型

無向圖。節點為參與者，邊帶有建立時間與所屬任務。同一對參與者的重複配對不重複計邊。

4.2　呈現方式

已否決　在角色之間畫連線

30 名參與者、每人配對數次，畫面會糊成毛球。視覺雜訊會壓垮手繪極簡的場景語彙。

提案　轉為 Boids 凝聚權重偏置

不畫任何線。改為讓配對過的參與者之間，Boids 的凝聚力（cohesion）權重略高於一般值。 社交圖譜於是表現為畫面上的自然群聚——互動過的人的角色會漸漸靠在一起， 形成幾個鬆散的團體。

這個作法零視覺雜訊、直接複用 M2 既有的群體動力引擎， 且剛好實現了 v2.0 原本描述的「依社交圖譜分群靠攏」——只是把它從合照當下的排版演算法， 提前成活動全程持續發生的空間現象。

已實作　強度待現場定案

已於 BOIDS.affinityBonus 實作，現值 1.5：配對過的鄰居 在凝聚質心中的權重為一般人的 2.5 倍。

實作過程釐清了一件事：偏置的作用不是讓熟人貼得更近 —— 分離力構成 95 單位的地板，凝聚力再強也擠不進去。它真正的作用是 決定角色往哪一群漂。測試以兩個相隔的群體驗證： 置於正中間的角色，在有社交連結時會明顯漂向熟人那一群（距離 29 對 98）， 無連結時則維持等距（72 對 77）。

強度仍需於 WP-C 現場實測定案 —— 過強會讓群體黏成硬塊、失去湧現感。

05主辦端控制台

系統的第三個角色。v2.0 只在 M4 觸發合照時提到主辦端，v3.0 將其獨立為完整客戶端。

任務控制

選擇任務類型、填寫參數、發布、監看即時完成進度、關閉任務。

現場處置

踢除特定參與者、暫停全場、重置場域。現場出狀況時的唯一處理管道。

收尾儀式

觸發最終合照與成果回顧，作為活動的結束標記。

資料匯出

匯出行為 Log 與社交圖譜，供 WP-C 與 WP-D 分析使用。

同時解決既有缺口

現場處置與資料匯出兩項，正好補上 1.0 版自評指出的兩個缺口： 無法處置惡意參與者，以及 WP-C 行為 Log 只存在記憶體、重啟即失。

07M4 重新定位

從核心產出降級為收尾儀式，同時修正一個語意錯誤。

降級理由。逐步累積的社交圖譜比一張擺拍合照更有力， 而且它在活動全程持續發生，不是最後三十秒的事。 「階梯分層排版演算法」與「4K 紀念框」的工程成本高、與破冰目標關聯低， 資源移往任務系統是划算的交換。

語意修正。合照應從參與者名冊（所有曾經進場的人）構圖， 而非從當下場上的角色構圖。婚禮、尾牙的合照記錄的是「這場活動有誰來過」， 不是「某個瞬間站在這裡的人」；早退者被排除在外，在社交意義上是失禮的。

連帶簡化

這個修正讓 M4 與即時狀態解耦：不再需要「合照前 N 分鐘內須有操作」的資格規則， 也不需要退出排除邏輯。退出功能仍然保留（讓人乾淨離場、停止角色漫遊）， 但不再影響合照資格。

09阻擋與待決事項

9.1　硬阻擋：相機需要安全情境

必須在開工前解決

手機瀏覽器在 http://192.168.x.x 上會拒絕相機權限。 getUserMedia 要求安全情境（HTTPS 或 localhost），區網 IP 不符合。 這是瀏覽器的硬規則，不是可以繞過的設定。

可行方案各有代價：自簽憑證會跳出安全警告，在活動入口嚇退參與者； 真實憑證需要網域與 DNS 配置。這是「拍攝現場照片」任務延後的主因—— 不是功能難做，是部署條件未備。

9.2　搶答的公平性

搶答順序取決於封包抵達順序，而封包抵達順序取決於各人的 Wi-Fi 訊號強度， 不是反應速度。實測管線延遲 p50 為 18.1ms、p99 為 49.3ms（不含現場 Wi-Fi）， 這個離散程度足以決定勝負。要做得公平需要客戶端時間戳加上伺服器校時，是另一套工程。

9.3　既有的規格內部矛盾

v2.0 同時要求「搖桿輸入 20 Hz 節流」與「輸入延遲 < 50ms」，這兩者無法同時成立： 節流佇列本身最差就佔滿 50ms 預算。需決定調整節流頻率或修訂驗收標準。 伺服器 CPU 餘裕充足（30 角色時每 tick 僅 0.011ms，佔預算 0.03%），提高頻率在技術上可行。
