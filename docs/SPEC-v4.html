PersonaFlow 立體場域架構

場域由 2D 手繪畫布轉為 Three.js 立體空間，角色由 SVG 模組捏臉轉為 AI 生圖驅動的骨架模型 —— 角色從「飄移」變成真正的行走。 後端整套保留，本次替換的是渲染層與角色資產，不是系統。

版本 v4.0 基準 規格 v3.0 仍然有效 v3.0 §03 任務系統 · §05 主辦端 實測期限 9/30

00改版摘要

小組決議三項變更：掃描生成角色、場景立體化、角色真正行走。

項目v3.0v4.0狀態
角色生成 手機端結構化模組捏臉 掃描人物 → AI 生成去背積木人偶圖 → 切片貼到共用 3D 模型 生圖已完成
場域呈現 2D 手繪畫布（Canvas2D + rough.js） 3D 立體場景（Three.js） 技術已驗證
角色運動 程式化 2D 步態（彈跳擺動，觀感為飄移） 骨架動畫，真正的行走循環 本階段重點
合照分發 規劃中 QR Code 下載 已完成
M2 共治引擎 — 完全不變 沿用
任務系統與主辦端 — 完全不變，另需納入場景控制 沿用
給 R4 的論述提示

技術文件 v2.0 曾明確「移除高延遲 CVAI 影像辨識，捨棄不穩定的相機拍照與純 AI 全圖生成」。v4.0 把掃描拉回來，WP-D 必須重新交代這個轉折 —— 否則答辯時會被問「你們不是說這條路不穩定嗎」。

可用的論證方向：v2.0 移除的是「即時全圖生成」（延遲不可控、結果不可預期）； v4.0 採用的是「生成一次、綁定到預先驗證過的骨架」， 生成發生在進場當下而非每一幀，延遲與失敗都可被隔離處理。 這是兩種不同的技術路徑，不是推翻先前的判斷。

01存活與汰換

先確認範圍：這次動的是渲染層與角色資產，後端一行都不用改。

保留

Gateway、連線防護、固定頻率時脈、M2 共治引擎（α 仲裁 + Boids）、 任務系統、配對、社交圖譜、主辦端控制台、手機控制器的搖桿與任務介面。

汰換

shared/avatars.js（SVG 捏臉組裝）、 public/screen/ 全部（2D 渲染器、手繪場景、程式化步態、道具）。

為什麼 M2 完全不用改

M2 輸出的是地面平面上的位置與速度，它從來不知道畫面是 2D 還是 3D。 更關鍵的是，STAGE_SYNC 現在送的 state: WALK / IDLE 加上 vx / vy，正好就是驅動 3D 骨架動畫混合所需要的輸入 —— 當初為 2D 步態設計的欄位，換到骨架動畫一樣夠用。

障礙物在 2D 是地面上的圓，在 3D 還是地面上的圓。避障、社交群聚、 邊界回推、剛體修正全部原封不動。

建議保留 · 捏臉作為備援

既有的三步捏臉流程請不要刪除。相機權限被拒、光線不足、 生成失敗都是現場一定會發生的事，屆時需要第二條路讓參與者仍能進場。 這套流程已經寫好且通過測試，留著不花成本。

02座標與架構

邏輯平面直接就是 3D 地面，這是後端得以完整保留的原因。

2.1　座標映射

伺服器（邏輯 2D）Three.js（世界 3D）說明
x ∈ [0, 1920]world.x場域寬度，直接對應
y ∈ [0, 1080]world.z俯視圖的縱深，成為 3D 的深度軸
—world.y = 0角色站在地面；Three.js 為 Y 軸向上
vx, vy朝向角 = atan2(vy, vx)由渲染端自行換算，伺服器不需送角度
給 R2 的實作提醒

速度趨近 0 時 atan2 會劇烈跳動，角色會原地亂轉。 渲染端必須自行維護一個平滑後的朝向角，並在速度低於門檻時保持上一次的朝向。 facing 欄位（±1）在 3D 已不足用，但保留無害，可作為初始朝向。

03角色管線

把「掃描生成」與「骨架」解耦，是這條路能走通的關鍵。

生圖的產出格式決定了整條管線

生圖系統產出的是正面直立、去背景的積木人偶全身圖。 這個格式有三個性質，讓原本困難的問題變得單純：

  1. 構圖固定 —— 每一張的姿勢與取景都一樣，不是任意輸入
  2. 分件規格化 —— 頭、髮、軀幹、雙臂、雙手、臀、雙腿，每一隻都相同
  3. 剛體關節 —— 積木人偶只在肩與髖轉動，身體不會變形

3.1　為什麼這不需要一般意義的「綁骨架」

一般人形角色要綁骨架，是因為皮膚必須跟著骨頭變形（skinning）， 需要逐頂點的權重繪製，這才是耗時且需要專業技能的部分。

積木人偶完全不需要蒙皮。它就是一組剛體的父子關係 —— 九個節點，每個節點是一塊不會變形的實體。所謂「綁骨架」在這裡只是 把模型的各部件依正確的階層接起來，是建模時就順手完成的事。

3.2　行走可以用程式算，不需要動畫剪輯

積木人偶的走路，全部內容就是大腿繞髖部、手臂繞肩膀做反相擺動。 這正是技術文件「程式化步態，無逐格動畫成本」的同一套作法 —— 2D 版本已經以正弦函式實作過一次，換到 3D 只是把數值套到關節旋轉上。

連帶結論

不需要 Mixamo，也不需要任何動畫剪輯檔案。 沒有動畫檔就沒有格式轉換、沒有重定向、沒有授權問題。 R4 的任務從「學會綁骨架與匯出動畫」縮減為「做一個分件正確的積木人偶模型」。

3.3　管線

01掃描 手機相機拍攝參與者（需安全情境，見 §08）
02生成 既有系統產出去背景的積木人偶全身圖
03正規化 裁到 alpha 邊界、縮放到固定高度，消除構圖誤差
04切片 依固定比例裁切框切出頭／軀幹／腿，成為貼圖
05貼圖 套到共用的積木人偶模型對應部件
06行走 程式化擺動關節，與生成品質無關

第 03 步的正規化是可靠度的來源。先裁到 alpha 邊界再縮放， 後續的固定比例裁切框才會穩定命中同樣的部位；直接對原圖套裁切框， 構圖只要有一點偏差就會切歪。

R1 第一週要驗證的事

拿約 20 張實際生成結果，確認正規化後各部件是否穩定落在同一比例位置。 若一致，固定裁切框即可；若有明顯浮動，才需要加入偵測步驟。 這個驗證便宜且能及早排除最大的未知數。

3.4　背面貼圖

生成的是正面單視角，但 3D 模型有背面。對於群體俯視的場景， 背面採用由正面取樣得到的單色即可，觀眾在那個距離看不出差異。 若日後要提升，再考慮生成第二張背視圖，但這不該排進本期時程。

3.5　生成失敗的備援

走路是模型與程式帶來的，與生成結果無關。因此生圖失敗時， 只要退回預設貼圖，角色依然能正常行走與參與任務 —— 失敗會降級為「外觀不像本人」，而不是「無法進場」。 再加上保留的捏臉流程作為第二條路，現場不會出現無法參與的狀況。

043D 渲染引擎

這是原本分工清單裡漏掉的一項，而它是最大的單一工程量。

「3D 場景建模」與「角色骨架」都是美術資產任務。 但把 Three.js 接上 STAGE_SYNC、載入模型、驅動骨架動畫、 處理相機與光照、移植任務橫幅與完成回饋 —— 這個引擎整合 才是工作量最大的部分，必須列為獨立項目並指定負責人， 否則它會變成「大家以為別人在做」的那一項。

4.1　引擎需要完成的事

項目說明
場景載入與相機載入場景 glTF，設定投影用的固定機位與光照
角色池共用骨架與動畫剪輯，每位參與者一個實例；需支援中途進出場
狀態驅動動畫state 切換走路／待機，速度決定播放速率
朝向平滑由 vx / vy 換算並平滑，低速時保持前一次朝向
位置內插伺服器 30 Hz、畫面 60 Hz，需內插否則有階梯感（2D 版已有可參考的實作）
任務回饋任務橫幅、完成提示、配對成功的視覺強調
合照取景收尾時的相機運鏡與畫面輸出
效能守則

目標是 30 個骨架角色維持 30 FPS 以上。務必：模型低面數、 共用材質與貼圖（每個人一張獨立貼圖會讓 draw call 爆掉）、 骨骼數量克制。第一週就用 30 個佔位角色壓測， 不要等到資產完成才發現跑不動。

05五份介面契約

分工失敗通常不是分錯，是介面沒先講好。第一週把這幾件事定案，五條線就能各做各的。

契約 1 STAGE_SYNC 不變 R3 → R2

渲染器只吃以下欄位，伺服器保證不改動。每秒 30 次廣播。

{
  id:      "usr_8f9a2b",   // 參與者識別碼
  x, y:    數值,            // 邏輯座標 → world.x / world.z
  vx, vy:  數值,            // 合成後的速度，用於行走播放速率
  heading: 弧度,            // 完整朝向角，已由伺服器平滑並在靜止時保持
  state:   "WALK" | "IDLE", // 行走／待機切換
  mode:    "ACTIVE" | "SWARM" | "STAGED",
  alpha:   0 ~ 1,           // 主動控制權重
  facing:  1 | -1,          // 2D 備援版本用；3D 請用 heading
  offline: 布林,
  emote:   "CHEERS" | "HEART" | "WAVE" | null,

  // 以下兩欄只在有意義時才出現，未出現時視同預設值
  emoteT:  0 ~ 1,           // 社交動作進度，用於對齊動畫相位
  arrived: true             // 定位鎖定且已就位
}

朝向由伺服器計算，渲染端不要自行從 vx / vy 推算。 速度趨近 0 時 atan2 會劇烈跳動，需要「靜止時保持前一次朝向」的狀態； 而大螢幕與合照是兩個渲染端，各算一套必然不一致 —— 合照當下角色的朝向會與觀眾前一秒看到的不同。

契約 5 定位鎖定（合照用） M2 → M4

M2 提供把角色平滑帶到指定座標的機制，但不決定隊形。 誰站哪、怎麼排是 M4 的決策，因此排版演算法可以任意更換而完全不必動 M2。 

// 指派定位。heading 為到位後的朝向，合照時通常全部面向鏡頭。
stage.lockStage(new Map([
  ["usr_8f9a2b", { x: 900, y: 700, heading: -Math.PI / 2 }],
  ...
]));

// 輪詢直到全體就位。不要用固定秒數等待 ——
// 移動時間取決於角色原本散得多開。
if (stage.allArrived()) { 拍照 }

// 拍完解除，角色平滑重新加入人群
stage.unlockStage();

鎖定期間使用者操控與群體動力都不生效，接管與解除都是漸進的 （ARRIVE.takeoverMs，現值 600ms），對應技術文件要求的「角色平滑移向」。 角色以抵達式轉向前進並在接近時減速，不會衝過定位再折返。

契約 2 模型節點階層與命名 R4 → R2

渲染程式以節點名稱取得關節並施加旋轉，命名一旦變動程式就會靜默失效 （角色會站著不動，而不是報錯）。階層固定為： 

Root
└ Hips              ← 位置與朝向由此驅動
  ├ Torso           ← 貼軀幹貼圖
  │ ├ Head          ← 貼頭部貼圖
  │ │ └ Hair
  │ ├ Arm_L → Hand_L   ← 繞肩擺動
  │ └ Arm_R → Hand_R
  ├ Leg_L           ← 繞髖擺動
  └ Leg_R

要求：各關節的旋轉軸心必須落在真實轉軸上 —— 手臂的軸心在肩、腿的軸心在髖，不是在部件中心。 軸心放錯會讓角色走路時肢體從身體上脫開。

貼圖以 Tex_Head、Tex_Torso、Tex_Legs 三張為掛載點，對應 §3.3 切出的三塊。

契約 3 場景碰撞佈局回寫 R5 → R3 / R2

3D 模型裡的沙發座標，必須與伺服器 shared/scene.js 的障礙物清單一致， 否則角色會直接穿過家具。模型是視覺，碰撞是資料，兩者必須人工同步。 建模完成後要把每件道具的座標與碰撞半徑填回： 

PROPS = [
  { id: "sofa_1", type: "sofa", x: 1452, y: 622, r: 84 },
  ...
]

現有的 npm run preview:scene 會把碰撞半徑畫成黃色虛線圈， 可用來核對是否與模型對得上。

契約 4 角色外觀資產 R1 → R2 / R4

掃描與生成的最終產出：三張已正規化並切好的貼圖， 加上供背面與備援使用的取樣色。這份 schema 決定 R4 的 UV 分區與 R2 的載入邏輯。 

{
  userId:   "usr_8f9a2b",
  textures: {
    head:  "/assets/gen/usr_8f9a2b/head.png",
    torso: "/assets/gen/usr_8f9a2b/torso.png",
    legs:  "/assets/gen/usr_8f9a2b/legs.png"
  },
  // 由正面取樣，用於背面與側面的單色填補、以及貼圖載入前的替身
  fallbackColors: {
    skin: "#F4C08A", hair: "#4A2C1A",
    torso: "#8FA05E", legs: "#B7A98A"
  }
}

貼圖以 檔案 URL 而非 base64 傳遞。30 人的貼圖若內嵌進 STAGE_ROSTER 會讓名冊訊息膨脹到現場無線網路難以負荷； 走 URL 則可由瀏覽器自行快取與並行下載。

第一部分資產與探索並重，第二部分整合並讓 R4、R5 回到本業。

6.1　第一部分

角色主責完成的判準

他們本業的工作（論述、實測腳本）在系統穩定前推不動，此時有餘裕； 第二部分再回到自己的線。這是依「各人何時有空檔」分配，而非只按職稱。

6.2　第二部分

角色主責完成的判準

R2 正式場景與角色就位 ＋ 合照取景運鏡 佔位資產全數換成正式資產；合照能框住全體
R3 場景納入後台控制 ＋ 合照輸出接上既有 QR 分發 主辦端能切換場景／燈光；合照能產出並分發
R4 回到 WP-D，論述隨架構調整（見 §00 的論述提示） 期末報告與答辯簡報

最重要的一條排程規則

R2 不能等 R4 的模型。第一天就用幾個方塊組成的假人偶 當佔位 —— 只要節點階層與命名符合契約 2，R2 就能把整套朝向、行走擺動、 位置內插、30 人壓測全部做完，最後只是把模型換掉。 這個假人偶 R2 自己十分鐘就能拼出來，不必等任何人。 這一步能省掉一到兩週的串行等待，是五人分工能否真正並行的關鍵。

07時程與備援

時程現實

距 WP-C 的校內實測（9/30）只剩約五週半。 要在這段時間完成 HTTPS 部署、掃描管線、3D 場景、骨架、渲染引擎重寫、 合照取景 —— 對五位還有其他課業的同學來說非常緊。

因此：2D 版本不要刪

現行的 2D 系統已通過 71 項單元測試與 46 項端對端測試，是一個完整可運行的版本。 請在另一條分支上開發 3D，隨時保持「至少有一個版本能跑」。

如果 9/29 晚上 3D 仍有問題，可以用 2D 版完成實測、取得 N ≥ 25 的資料， 而不是開天窗。這一條可能比任何技術選擇都值錢。

7.1　關鍵路徑

最長的依賴鏈是：HTTPS → 掃描 → 生成 → 參數萃取 → 角色轉譯。 這條鏈上任何一環卡住，整個掃描功能就不存在。因此 HTTPS 必須在第一週解決， 它現在是 P0，不再是「之後再說」的項目。

3D 渲染引擎與美術資產是可並行的第二條線， 只要遵守 §6.2 的佔位資產規則就不會互相阻塞。

08待決事項

8.1　硬阻擋：相機需要安全情境

P0 · 第一週必須解決

手機瀏覽器在 http://192.168.x.x 上會拒絕相機權限。 getUserMedia 要求安全情境（HTTPS 或 localhost），區網 IP 不符合。 這是瀏覽器的硬規則，不是可以繞過的設定。

可行方案各有代價：自簽憑證會在活動入口跳出安全警告嚇退參與者； 真實憑證需要網域與 DNS 配置。沒有它，掃描功能完全不存在。
