# 生成管線：風格、VLM 與貼圖

> 由 [CLAUDE.md](../../CLAUDE.md) 拆出。這裡是踩過的坑與當初的取捨理由 ——
> 動到相關程式碼之前先讀，多數條目都附了「不這樣做會怎樣」。

### 切片比例是跨語言耦合

`backend/slicer.py` 的 `CUTS` 與 `shared/avatars.js` 的 `CV_CUTS` 必須完全一致 ——
一邊照比例切、一邊照比例疊回去。對不上時角色會脖子錯位或腿被壓扁，
**而且兩邊都不會報錯**。`backend/tests/test_slicer.py` 有測試直接比對兩邊數值。

### 風格的四樣東西必須成套

一個生成風格由四件事構成，全部掛在 `style_registry.GenerationStyle` 上：
prompt 模板、negative、姿勢參考圖（`pose_builder`）、策展參考圖集（`reference_set`）。

**任兩個風格共用其中任何一項，都不會報錯。** 參考圖集在 prompt 裡被明文宣告為
「工藝的最高權威」（`_ROLE_STYLE`），所以拿樂高的 sheet 配皮克斯的 prompt，
模型只會自己選一邊 —— 現場看起來像模型不穩，不像配錯檔案。姿勢參考同理：
樂高那張畫的是梯形軀幹加爪手，餵給皮克斯會把玩具比例一起帶進去。

`STYLE_REFERENCE_SET` 現在是**全域覆寫**而非主要來源。設了它就會把所有風格
壓到同一組圖，也就是上面那個錯誤配對。平常留空；被覆寫的風格會出現在
生成服務 `/health` 的 `degraded` 裡。`backend/tests/test_style_registry.py`
擋住共用，並檢查每個風格指名的圖集在磁碟上真的存在。

### 風格可以先接線、後備圖（`ready=False`）

一個風格的程式碼（prompt、negative、姿勢參考、role 文字）寫完，不代表它可以上線 ——
策展參考圖集要另外備，而那件事的瓶頸不是寫程式。中間這段期間的正確狀態是
**查得到、選不到**：`GenerationStyle(..., ready=False)`。

- `list_styles()`（手機端選單、`/health` 的 `styles`）不含它；
  `has_style()`／`resolve_style_id()`／`get_event_style_id()` 一律當它不存在。
- `get_style()` 與 `list_all_styles()` 仍看得到它，所以測試、工具腳本、
  `/health` 的 `style_reference` 都能檢查它。
- `/health` 的 `degraded` 會寫「尚未上線」而不是「參考圖集缺失」——
  **「圖還沒備」與「這個風格根本沒註冊成功」必須分得出來**，前者是進行中的
  工作，後者是事故，而兩者在只看 `styles` 清單時長得一模一樣。

不這樣做的話只有兩個選擇，兩個都更糟：讓沒有 sheet 的風格出現在選單上
（參與者選了，生成不會失敗，只是每個角色各自漂移，看起來像模型不穩），
或者等圖備齊才寫程式（那幾張圖要照著 prompt 的規格畫，順序是反的）。

缺圖的目錄裡要放一份 **INTAKE.md** 寫清楚要提供什麼圖 ——
`backend/tests/test_style_registry.py` 會檢查它存在。沒有它的話，
「還差什麼」只存在某個人的腦裡，而備圖這件事通常隔幾週才回頭做。

`pixel`（像素）走過一次這個流程：2026-09-23 先接線、2026-09-24 圖到位後上線。
目前沒有風格處於這個狀態，機制由 `PendingStyleTests` 用一個臨時註冊的風格守住
（不綁在某個剛好還沒上線的風格上，否則它一上線，測試就跟著消失）。

### 像素風格：格數是跨三份檔案的耦合

`garment_gen.PIXEL_ART_GRID_HEIGHT`（角色高 75 格，2026-10-15 前是 90）必須同時成立於
三個地方：prompt 的文字、素體（姿勢參考圖）、以及策展圖的規格（INTAKE.md）。對不上時模型會在同一次請求裡收到兩種格距，輸出的格子大小
就會每張都不一樣 —— 三邊都不會報錯。`PixelStyleTests` 擋住這一條。

格數是**策展參考圖自己的格距**（現在這組角色高約 650px、一格約 8.6px）。
先前設 64，理由是投影機：大螢幕上角色只有 130~170 個裝置像素高，64 格時一格
約 2~3 個裝置像素，最能看出是像素畫。**做出來被否決了** —— 64 格把臉壓成馬賽克，
而這件作品的核心是參與者認得出那是自己。代價是格子細時投影機上一格只剩兩個
裝置像素上下，顆粒感主要靠手機確認頁成立。**兩邊都只能在真投影機上判斷**，開發機視窗大、
角色被放大，看不出差別。

**策展圖不要重新定格，也不要量化**（實測 2026-09-24，走過兩次死路）。
生圖模型產的「像素風插畫」格距是浮動的（一格 7.9~8.1px、每張偏移不同），
硬切成 64 或 90 格都會讓每個輸出格混到隔壁格：邊緣密度從 0.056 掉到 0.045，
肉眼是糊掉、變髒，而檔案看起來仍然很「像素」，所以很容易被當成正常。
量化同樣不能做：中位切割照面積分配色票，虹膜那種小面積關鍵色會被併掉 ——
64 色時綠眼睛變藍眼睛。`scripts/prepare_turnaround_reference.py` 因此只洗不畫：
清背景、依 `layout.json` 重排三視圖，人物像素與原圖相同。

同一類的坑還有比例：prompt 原本寫 4.5 頭身、姿勢參考圖畫 4.4 頭身，而策展 sheet
是 3 頭身 —— 三邊不一致的結果不是折衷，是**三邊都不聽**，模型逕自畫成 7 頭身的
寫實比例（實測 2026-09-24）。現在三邊都是量自 sheet 的同一組數字（頭含髮 45%、
領口 49%、腰 72%、鞋頂 92%，約 2.2 頭身），素體照同一組圖畫，且 `_ROLE_STYLE_PIXEL`
明文把「頭身比」交給 sheet 決定。

輪廓墨色 `PIXEL_INK` 與 `public/screen/scenes/pixelKit.js` 的 `INK` 是同一支
（`#302a2d`）。角色會站在像素廚房／辦公室前面，兩邊的黑不同調時角色會像
貼上去的 —— 而分開看兩邊都很正常。測試會比對這兩個值。

生圖模型交出來的**不會**是合格的像素畫，而是像素風插畫：格距浮動、邊緣帶
反鋸齒、上萬種顏色。參考圖的規格與整理流程見 `2026q3_pixel_curated/INTAKE.md`：
1536×864 三視圖、剛好三個人、腳底同一條線，`PixelStyleTests` 與
`scripts/check_reference_set.py` 擋住這些。

**「grid」會被照字面畫出來**（實測 2026-10-14）。像素 prompt 反覆講格子，
模型有一次交出整片方格紙背景。去背只灌得進「連到邊界的白」，格線把白底切成
封閉小格，結果人偶連同方格紙一起留下，而連通性、雙腿、出框檢查全部通過 ——
前景佔比 0.81，剛好擦過舊的 0.85 上限。現在 prompt 明文說格子是隱形的，
`avatar_quality` 另加 `background_left`（佔比 > 0.70；三種風格正常輸出最高 0.57）。
**不要把這個門檻往上調**，0.85 那條擋的是另一件事。

還沒解決的一項：貼圖從生成到投影會經過兩次**平滑**重新取樣
（`slicer.normalize()` 的 LANCZOS、大螢幕的 `imageSmoothingQuality='high'`）。
64 格時撐得住，格子更細之後投影機上一格只剩兩個裝置像素上下，這一項從「先不改」
升級成投影驗收要特別看的項目。要改的話必須讓渲染端知道角色是哪個風格，
而 `/generate` 回的 `styleId` 目前並沒有被帶進 `pendingScanConfig` 與名冊 ——
那是一整條獨立的接線。

### VLM 預設關閉，而且模型名不可寫死

服裝／臉部的 Gemini 呼叫由 `FULL_MODE_VLM_ENABLED` 控制，**預設關閉**，
`service.py` 讀 `config` 的同一個欄位。

關閉是因為生圖模型本來就收到原始照片，這兩次呼叫是重複的視覺分析；
而 Gemini 免費方案是**每個模型每天 20 次請求**，一位參與者吃掉 2 次 ——
開著的話一天只夠 10 個人，第 11 個人開始靜默退回純 CV 顏色。

兩個踩過的坑：

1. **模型名不可寫死。** `gemini-2.0-flash` 曾寫死在 `vlm_module.py` 兩處，
   Google 讓它退役後兩支都回 404，VLM 全數失敗 —— 但**生成照樣成功**，
   只是 prompt 裡的髮色／髮型／眼睛／鬍子／服裝款式欄位默默全空。
   錢照付、東西拿不到，畫面上完全看不出來。現在走 `config.VLM_MODEL`，
   且模型物件在**呼叫當下**才建立（存成模組常數等於凍結在 import 當下）。

2. **測試必須把 VLM 也 stub 掉，不只生圖。** `test_service.py` 的 fixture
   原本只替換 `generate_full_character_png`，於是每個 `/generate` 測試都對
   Gemini 發兩次真實請求。長期沒被發現是因為那個模型已退役、秒回 404，
   看起來只像「有點慢」；模型修好之後整個套件從 20 秒變成 86 秒，
   而且每跑一次測試就付一次錢，還會吃掉當天的配額。

`/health` 會回報 `vlm_enabled` 與 `vlm_model` —— 「關著」與「開著卻一直失敗」
在現場長得一模一樣（兩者都是 prompt 少掉語意欄位），不報出來分不出來。

### style_registry 只能有一份（雙重匯入路徑的陷阱）

`backend/` 底下同時存在兩種匯入寫法：`from backend.style_registry import ...`
（garment_gen 用）與 `from style_registry import ...`（service.py 用，因為它以
`python backend/service.py` 啟動，`sys.path[0]` 就是 `backend/`）。

兩條路徑**都成立**的時候（pytest、或任何把專案根目錄放進 `sys.path` 的環境），
Python 會建立**兩個獨立的模組物件**，各自帶一份空的 `_STYLES` ——
garment_gen 把風格註冊進其中一份，service.py 從另一份查詢，查到的永遠是空的。

後果全程無聲：沒有例外、沒有 log、`/health` 的 `degraded` 也是空的，
只是每一個請求都靜默退回預設風格。症狀是「選了皮克斯卻生出樂高」，
看起來像模型的問題。

`style_registry.py` 檔尾用 `sys.modules.setdefault()` 把兩個名字釘成同一個
模組物件來根除它。**不要刪掉那幾行**，也不要因為「看起來像多餘的魔法」而
改寫成一般的 import。`backend/tests/test_style_registry.py` 的
`SingleRegistryInstanceTests` 有回歸防護（拿掉那幾行會有兩個測試立刻失敗）。

任何**持有可變全域狀態**的模組都有同樣的問題；純函式模組則無所謂。

### 參與者選的風格是 per-request，不是活動層級

`CHARACTER_STYLE` 從「一場活動一種風格」降級成「參與者沒選時的預設」。
手機端的選單由 `/api/styles` 餵資料（Gateway 轉問生成服務的 `/health`），
**不要在前端寫死風格清單** —— 某個風格的參考圖集沒放進去時，後端會據實回報，
寫死的話選項照樣出現，選了卻靜默退回預設，參與者只會覺得按鈕沒作用。

`resolve_style_id()` 對認不得的字串一律退回預設而不是報錯（現場原則：掃描
失敗一律降級，不擋人進場），因此 `/generate` 的回應帶 `styleId` 說明實際採用
的是哪一個 —— 沒有這個欄位就看不出退回發生過。

### 貼圖走 URL，不走 base64

30 人的貼圖若內嵌進 `STAGE_ROSTER`，名冊訊息會膨脹到現場無線網路難以負荷。
`roster()` 只在名冊變動時廣播，`snapshot()` 每幀 30Hz 只送座標 —— 這個分離要維持。

### 渲染程式碼放 shared/，兩端 import 同一份

`shared/character.js`（程式化步態）與 `shared/avatarSprite.js`（貼圖組裝）
同時被大螢幕與手機端 POV 畫布使用。**不要為了方便在手機端另抄一份。**

抄一份之後 `BOB_OMEGA` 之類的常數就成了第二份事實來源 —— 改了一邊另一邊
不會報錯，只會默默走出不同步頻，或讓「手機上的我」與「大螢幕上的我」長得不一樣。
與上面的切片比例是同一類跨檔案耦合。`EMOTE_GLYPH` 因為同樣理由放在 `shared/protocol.js`。

### 像素風一次生成三視圖：正面、右側、背面（2026-10-14）

角色完全平面，只有四面：往前走正面、往右右側、往左左側（＝右側鏡像）、往後背面。
哪一面由伺服器的 `view` 決定（`arbiter.js` 的 `updateView`）。走路時整張圖約 1.2%
身高的上下起伏，手腳擺動見下一節。

側面與背面**來自生成，不是程式推導**。像素風的生圖請求本來就只有一次，現在要求
模型在同一張 16:9 的圖裡由左到右畫出「正面｜右側｜背面」三個同一人，
`backend/turnaround.py` 切成三張，存成 `full` / `side` / `back.webp`。
不多花錢、不多等，三張出自同一次生成，衣服髮型顏色自然一致。

**四件事必須成套**（與「風格的四樣東西必須成套」同一類，對不上都不會報錯）：

- **prompt**：三視圖的排列、朝向（側面朝右）、同一基準線、中間留白。單一置中的
  舊指令要拿掉，否則兩段互相矛盾。
- **姿勢參考圖**：素體三視圖 `pose_turnaround.png`（2026-10-15 前是程式畫的灰色方塊）。
  若仍是單一站姿，prompt 要三個、參考圖畫一個，模型會自己挑一邊。測試會用我們自己的
  切割器切它，切不出三個人就失敗。
- **輸出比例**：`image_config.aspect_ratio = 16:9`。1344×768 時角色高約 700px、
  一格約 7.8px，正是策展原圖自己的格距。
- **策展 sheet**：2026-10-15 起是 4 張三視圖（`turnaround_*`，拼成 2×2），role 文字
  明寫「排法就是要畫的排法」。規格與流程見 `2026q3_pixel_curated/INTAKE.md` 開頭。

**切割的兩個坑**：

- **必須先切再去背**。去背會丟掉不連在主體上的孤島，三個人並排時另外兩個就是孤島。
- **不用固定三等分**，用白色欄的投影找人：模型不保證等寬等距。
  切不出剛好三個人時只留最左邊那個當正面（不是整張圖 —— 那會變成好幾個人黏成
  一個角色），側面背面從缺，角色照樣進場。
- **模型會把三視圖畫成「設計稿」**：第一張實測圖鋪滿格線、四邊加黑框，腳還踩進
  黑框裡。格線與黑框每一欄都有，整張圖被當成一個人、去背又被格線擋住，整張設定稿
  原封不動上場。兩道防線：
  1. prompt —— 負面提示詞原本還留著單張時代的「只能一個人、不准側面、不准三視圖」，
     和開頭互相矛盾，模型兩邊都想滿足就畫成設計稿。已改成明講「不畫格線、不加框」。
  2. `turnaround.clean_sheet()` —— 切之前把外框的近黑像素、細而長的直線（連同旁邊
     一圈反鋸齒淡灰）洗白。淡灰那圈不洗的話剛好擋住 flood fill，兩腿之間整條白縫
     被當成「圍起來的白色衣物」留下來。
- **手臂與身體之間被圍住的白縫要另外挖**（`turnaround._enclosed_gaps`）。去背從
  圖邊往內 flood fill，走不到被手臂與身體圍住的縫，原樣留成不透明的白 —— 手一擺，
  旁邊就是一條白邊。不能一律挖掉被圍住的白（白上衣、白鞋、眼睛反光靠這條規則
  留下來），判定是縫要同時成立：亮而且幾乎沒有顏色（縫裡常有沒洗乾淨的淡灰格線，
  只看純白會被切成好幾小塊）、窄、高比寬長（白袖口是橫的）、在手臂高度
  （眼睛在上面）、在手臂與身體之間（貼著輪廓外緣的是袖子上的白條紋）。只給正面
  與背面。兩個被否決的判定：「縫裡原本有格線」（白上衣的摺痕、眼睛的描邊也是
  細直線，上衣被挖出一堆洞、眼睛反光也被挖掉）；「縫的兩邊都是深色描邊」（模型
  常讓縫直接貼著膚色或衣服色，粉紅洋裝的縫大半過不了）。
- 整張原圖存在 `backend/logs/generated/<id>_full_character_0_sheet.png` 備查；
  主控臺歷史與角色用的是切好、去背的正面，側面與背面存在 `public/assets/gen/<id>/`。

**三面之間不一致的兩件事**（2026-10-15 回報）：

- **配件時有時無**（正面背面有背帶、側面沒有）：「三面一致」這種抽象要求模型不會
  逐面檢查。prompt 改成逐種配件講出每一面長什麼樣（斜背包：正面背帶斜過胸前、側面
  背帶過肩包在臀側、背面背帶斜過背）。VLM 開著時（`FULL_MODE_VLM_ENABLED`）另外
  列出照片裡的配件清單（`accessories`），**預設關閉時只有逐面的規則**。
- **頭身比不一**（同一批有 3 頭身也有近 5 頭身，大螢幕上每人總高相同，看起來個頭
  不一）。30 人同時生成，不能靠「不合格就重生」，要一次就對，所以從輸入下手：
  1. 參考圖集改成三視圖，排法與輸出相同 —— 側面背面不再靠模型自己想；
  2. 姿勢圖改成**素體**：同一個畫風、同一個身材的人，模型把衣服穿到它身上，
     身高與頭身比都來自同一個身體（灰色方塊沒有臉、沒有畫風，常輸給照片）；
  3. 照片那一行的 role 明寫「不取照片的體型」（原本只說臉、膚色、頭髮、衣服照抄，
     模型連真人的頭身比一起抄）；prompt 的比例數字改成量自新參考圖的那組。
  試過以程式量頭身比當重生門檻：策展參考圖自己就量出 0.19～0.54，量不準，否決。
  4. **以上都做了還是飄**（2026-10-16 量最近的角色，下巴落在身高的 28%～42%，素體是
     42%）。同一張照片重生一次，結果可以從 5 頭身變 2.7 頭身 —— 不是哪一步壞了，是
     Q 版像素沒有像樂高小人偶那樣模型背熟的標準身材，每次都在跟照片拉扯。所以後端
     直接收：`turnaround.fit_base_body` 量正面的下巴，頭不動、下巴以下整段垂直縮放，
     讓下巴落在素體的位置（`BASE_BODY_CHIN`），三面用同一個倍率。**不看真人比例，
     每個人都是同一個物種**（展方決定；以後若做矮／中／高素體，換 target）。
     - 下巴用「臉的左右跨度」量，不用膚色格數：眉毛、眼睛橫過臉，那幾列只剩眉心一條
       膚色連著，窄得像脖子；短於 1.5 格的窄段略過。最近 16 個角色的下巴線逐張目視過。
     - 膚色的取樣段改成身高 12%～30%：原本 20%～42%，4 頭身的角色取到米色上衣。
     - 倍率下限 0.5：下巴 0.2 的硬壓到 0.42 會壓成一團，只收一部分。
     - 否決的作法：素體當成「要編輯的圖」放第一張（多畫一個人、照抄照片裡的手機與
       塑膠袋、身體反而變高）；每人同時生兩張挑比例近的（成本兩倍，且 30 人同時時
       生成服務負載未知）。
- **換了頭身比，走路分析的固定比例也要跟著**（2026-10-15）：側面的髖部原本固定在
  64%（3 頭身），2.2 頭身約 71%，腿會從腰上面擺；找手固定停在 74%，大頭角色的手垂到
  77%，手掌被切掉。新舊角色同時在場上，所以不改常數，改成量：髖部取「脖子到腳底的
  45%」，找手的範圍從脖子以下到正面量到的手掌（`rig.handRow`）。不用正面的胯下定
  髖部：寬褲的兩腿只有褲管底部分開，量到的胯下其實是褲腳。

**沒有側面／背面的角色一律畫正面**（舊資產、樂高、皮克斯、三視圖切失敗），
而且側面方向不鏡像正面。只是轉身時不換圖，不會出現怪圖。

**被否決過的做法**（都是 2026-10-08～14，現場一一回報）：

- 整張圖左右轉 ±5°：「人在抖」。
- 程式從正面推導背面與側面（在臉上塗頭髮、重組手腳、重新取樣半張臉）：每換一種
  髮型冒出一種新的怪圖 —— 長髮時判不出脖子，側臉橫切一刀、背面變禿頭。程式猜不出
  看不到的後腦勺與側臉。`shared/spriteViews.js` 只剩體素實驗與走路格（`findNeckRow`）在用。
- 紙娃娃（手腳剪下來繞關節轉）：「切面很詭異」。現在的手腳擺動是變形不是剪開，見下一節。

仍然成立的：

- **起伏的相位要每個角色自己累加**，不能用 `time × 步頻`：步頻隨速度變，
  time 是開頁到現在的秒數，轉彎減速時相位整段跳動。手機端的鄰居要帶 `id`、
  自己帶 `gaitKey`。
- **角色整體放大 1.12 倍**（`screen.js` 的 `CHARACTER_SCALE`），放在最後乘。

### 走路：手腳擺動從每一面各自分析（2026-10-14）

`shared/walkFrames.js` 對三張圖各自分析出手腳，以**變形**做出一個步伐循環的 8 格，
`shared/spriteCache.js` 在瀏覽器裡算成畫布快取，`drawCharacter` 依起伏同一個相位換格
（兩腳併攏時身體最高，那兩格就是原圖）。只給有三視圖的角色；其他只有起伏。

| | 怎麼找 | 怎麼動 |
|---|---|---|
| 正面／背面的腳 | 胯下的縫（借用體素實驗的 `segment`）；長裙找不到胯下時，從腳往上找中間有縫的那幾列 | 往前那隻往上縮 2 格（長裙 1 格）|
| 正面／背面的手 | **逐列**追手與身體分得開的那一段；肩膀與手碰到裙子的那幾列沿用最近一列的分界；下端停在最後一列有膚色的地方 | 與腳反向，往上縮 2 格、往中線收 1 格 |
| 側面的腳 | 腿的上緣 = 從腳往上，走到「最寬那一段」明顯比小腿寬（1.6 倍）的那一列，或碰到**下襬**（連續 3 列的主色不是小腿的顏色、也不是膚色）為止，先到的算 | 以髖部（大腿被裙子、短褲、長版上衣蓋住時以露出的第一列）為軸前後擺；腳掌整塊移動 |
| 側面的手 | 正面臉上取膚色，在手的高度找最大的一塊（露出大腿時只在**腿的上方**找），沿膚色接回肩膀，擬成一條直帶 | 前後擺；擺開後露出的身體補附近最常見的衣服顏色。只露出手掌（長袖）時不擺 |

不這樣做會出事、但不會報錯的地方（都是實測踩到的）：

- **變形，不剪開**：每一列的位移從關節的 0 漸增到末端，關節處不動，沒有切口。
- **位移一律整格**，而且以「格的列」算：同一格裡上下像素位移不同，那一格被扯斜，腳碎成好幾片。
- **以像素修正格子的標記**（`pixelLabels`）：我們取樣的格子（外框高 ÷ 90）與模型實際
  的格子差幾個百分點，往下數三十格就差一整格，描邊跨在兩格之間一半跟著走、一半留在原地。
  緊貼著會動區塊的深色描邊（半格以內）一律歸給那個區塊，畫的範圍也要包含它們。
- **格子透不透明看整格過半**，不只看中心點：手與身體之間的縫常不到一格寬。
- **手與衣服之間不透明的白縫，分析時當空的**（`openGaps`，與後端挖縫同一套判斷）。
- **手臂分界不能假設是直線**：體素實驗的 `segment` 取各列中位數，手往外斜的角色
  分界落在最外側，兩手都沒動。
- **手的下端停在手掌**：洋裝裙擺往外張，否則一路算到裙子底下，手一動裙邊被拉走。
- **膚色容差 32**：60 時粉紅洋裝（與膚色只差 46）整件被當成手。
- **膚色只收「紅 > 綠 ≥ 藍」且紅比藍多 30 的顏色**（2026-10-15）：臉的取樣範圍裡白衣領、
  粉紅的東西可能比臉多，大螢幕上白上衣角色的膚色量成白色、粉紅洋裝量成粉紅，側面
  整件裙子被當成手拉走、裙子碎掉。比對顏色時也看「綠減藍」：粉紅與膚色三通道只差
  40 上下，但膚色綠比藍多、粉紅藍比綠多。
- **大螢幕縮成 448px 時用最近鄰**（`spriteCache.prepareView`）：平滑縮小把相鄰兩格混成
  第三種顏色，膚色、描邊都量歪。**本機用原圖驗證過不代表大螢幕正常** —— 上面那個膚色
  的坑只在 448px 出現，驗證走路格要用與瀏覽器相同的尺寸與縮法。
- **側面兩腿疊在一起時複製一隻當遠側的腳**（壓暗），兩份反向擺；從中間切開會把一條腿撕成兩半。
- **側面找手只在腿的上方——只限露出大腿時**：短褲、短裙露出的大腿也是膚色而且比手大，
  實測大腿被當成手拉走、原地補成上衣的顏色（「大腿不見了」）。但長褲的腿一路到腰，
  手掌垂在骨盆旁、落在腿的範圍裡，一律限在腿的上方會把手掌切掉、只擺上半截手臂
  （2026-10-15 回報「手臂截肢」）。露不露大腿看膝蓋一帶（手掌垂不到的高度）：看腿的
  最上面幾列的話，長褲前面的手掌佔一半，會被當成光腿。
- **側面腿的上緣也看顏色**（2026-10-15）：側面的窄裙、短裙只比大腿寬一點，寬度擋不住，
  整件裙子被當成腿剪開擺動（回報「裙子側面變褲子」）。往上碰到小腿與膚色以外的顏色
  連續 3 列就是下襬；只看一列會被腳踝擋下（鞋口、襪子、陰影）。褲子一路同色找不到
  下襬，照舊靠寬度停在腰。
- **側面腿的上緣不找「突然變寬的那一列」**：手垂在下襬旁邊時下襬那一列不會突然變寬，
  找不到，腿的範圍一路包進上衣和手。改成從腳往上走到明顯比小腿寬為止，寬度看每一列
  最寬的那一段（兩腿張開站時整列外框是兩條腿加起來，量出來比裙子還寬）。
- **換裝角色的手臂範圍是事先做好的，不從圖上猜**（2026-10-20）：猜手臂是一直冒新例外的根源
  （長袖、斜背包擋住縫、寬袖、長髮）。換裝角色疊在同一個素體上，手臂位置已知：
  `layers/<素體>/_arms.png`（長袖外套另有 `top_hoodie_arms.png`）由 `scripts/dressup_arms.py`
  用同一套走路分析在素體上找一次、人工看過；組角色時 `dressup.arm_cells` 換算成大螢幕
  格子的座標，存 `arms.json` 跟貼圖放一起，`avatarSprite` 從側面貼圖的網址推出位置去讀，
  不必改傳輸格式（生成角色沒有這個檔，404 就照舊猜）。**外框要在整張三視圖上量**：去背會把
  圖裁小，從去背後的圖反推會整條往下偏 23 列、手臂落到腿上。改了素體、部件或找手的規則要
  重跑 `dressup_arms.py`。只對 2026-10-20 之後組的換裝角色有效（以前的沒存選了哪些部件，補不回）。
- **長袖沿著袖子兩側的描邊找整條袖子，小幅擺**（2026-10-20，「每個角色都要會擺手」）：只看得到
  手掌時，不能猜一條與手掌同寬的帶子（比袖子窄，一擺就把袖子撕成一條）。改從手腕到肩膀一次找
  一對最暗的路徑（`traceSleeve`：每列最多偏一格、偏了有罰分、寬度在手掌的 0.5–1.4 倍）。
  透明格要算最亮，算暗的話路徑直接滑到身體外。描邊不比布料暗、或肩膀到手腕橫移超過一個手掌
  寬（沿著頭髮、外套前緣走掉了），當作找不到、不擺。只擺 2 格：擺得越開，原地要補的布料越大
  塊，實測灰毛衣擺 6 格補出一塊深灰。10/19 之後的 32 個角色裡側面不擺的剩 2 個：手搭在光腿上、
  袖子線找錯被擋下。正面背面不擺的是斜背包垂在手旁邊、寬袖黏著身體（擋住手與身體間的縫）。
- **側面的裙子不動**：試過讓裙襬跟著腳晃，整格位移在裙邊切出階梯，現場回報「很破碎」。
- **側面腿露出來的第一列不動**：裙襬最底下幾排像素常落在這一列，跟著腿走會撕下一條。
- **側面手臂先收背光的陰影，再收描邊**（2026-10-20 回報「手臂一部分黏在軀幹上」）：手臂的帶子
  照膚色中心擬，偏向亮的一側；靠身體那側常有一條 1–2 格的暗膚色（跟膚色差 100 上下，容差收不到），
  它外面才是描邊。不收的話一條陰影加一條描邊留在身上。陰影的判斷是「膚色按亮度調暗後比對」
  （`skinShade`），不是放寬容差 —— 放寬會把粉紅、橘色的衣服收進來。
- **有袖子時手臂從袖口底下擺**，袖子不動：以前帶子一路延伸到脖子，但只有手臂寬、比袖子窄，
  袖子被撕成兩半，袖口的深色邊一半跟著手走。無袖的手臂往上沿膚色接回肩膀，照舊從肩膀擺。
- **側面手臂只吃緊鄰的深色描邊**，不固定多拿幾格：手臂常貼著衣服前緣，多拿的是衣服。
  深色要在 2 格內結束才算描邊：手掌垂在黑褲子前面時，兩側的深色是褲子，收進來的話
  一塊黑褲子跟著手走。
- **擺開後補的顏色取上下半格內最常見的**：取緊鄰第一格常是摺痕陰影，逐列各取會補出橫紋。
  深色與腿上的像素也算衣服：黑褲子整件都比描邊門檻暗、而且標成腿，排除的話手掌擺開
  原地補不出顏色，留下一個洞。
- **側面整個人朝左時後端鏡像**（`turnaround.face_right`，2026-10-15）：模型偶爾把側面
  整個畫成朝左（臉、領帶、鞋尖都朝左），大螢幕往右走時就倒著走（回報「頭是反的」）。
  看臉在頭的哪一側；膚色要用正面量的（`skin_tone`）—— 淺金、棕色頭髮也是紅多藍少，
  只看「像不像膚色」整顆頭都像臉。必須先於鞋子判斷：整個人朝左時鞋尖也朝左，先翻
  鞋子就變成頭朝左、腳朝右。去背後的圖要用 `_decode_rgba` 讀，`_decode` 會丟掉透明度。
- **側面只畫一條腿**（prompt）：模型把兩腿一前一後疊著畫、中間沒有空白時，走路分析
  分不出兩隻，複製出的遠側腿把兩隻都帶著走（回報「腳沒有分成兩隻」）。素體的側面
  本來就是一條腿，遠側那隻由走路動畫生出來；遠側腿不只壓暗，往灰收
  （`FAR_LEG_TONE`）—— 黑褲子壓暗還是黑，兩隻疊成一團。
- **側面鞋子畫反時後端翻正**（`turnaround.fix_backward_feet`）：模型偶爾把側面畫成人朝右、
  鞋尖朝左。整張鏡像會連臉一起反，只翻腳踝以下。只在兩腿疊成一條時判斷（鞋尖往哪伸
  一看就知道）；兩腿分開站時分不出哪隻反了，不動。
- **背面畫成側臉時丟掉背面**（`turnaround.back_shows_face`）：備援模型實測把第三個人畫成
  朝左的側臉。後腦勺是頭髮，頭那段的膚色只有耳朵後頸（主模型 26 張最多 3.4%），超過 5.5%
  就不要背面，大螢幕往上走時退回正面。用正面量到的膚色比，淺金髮的後腦勺不會被當成臉。
- **448px 高、每幀最多算 6ms**：用原圖 1024px 時 30 人要近 1GB；一口氣全算會卡幾百毫秒，
  超過預算的那幀先畫原圖。

**與 main 合併時的決定（2026-10-14）**：main 同時期做了另一套 —— 拍照角色在場上
縮成捏臉的 20×27 像素格子（`cvPixelSprite`），側面背面由正面推導、走路用捏臉的換格。
兩套互斥，生成角色的樣子與走路以這一套為準：

- `avatarImage()` 遇到拍照角色回傳 `cvAvatarImage`（生成的原圖 + 三視圖）；捏臉角色仍是
  `pixelAvatarImage` + `drawPixelCharacter`。
- 縮圖 `avatarPortrait`（主辦端、手機的頭像）後來也改用同一張生成原圖（`cvPortrait`），
  `cvPixelSprite` 從此沒有任何路徑會走到，2026-10-15 連同它專用的十多個輔助函式移除。
  commit `7ca0906`「大頭變香菇」修的脖子搜尋範圍就在這段，因此一併消失 ——
  場上用的是生成原圖，本來就不經過那段推導。
- 手機的腳步震動：捏臉角色依走過的距離（`stepIndex`），拍照角色讀 `gaitPhase('self')`，
  起伏最低點（兩腳張到最開）震一次。不要另算一份相位，步頻一改就與畫面錯開。
- 手機的場景視角（自己與鄰居）也要帶 `view` 與 `id`／`gaitKey`，否則手機上永遠是正面。
  伺服器的鄰居資料（`clientView` 的 neighbors）因此也帶 `view`。

### 體素 3D 角色（實驗，預設關閉）

**大螢幕預設不用**，網址帶 `?voxel=1` 才開。做過一版之後決定角色維持平面
（背景是 2D 的，立體角色站在平面場景裡不協調），程式留著供比較。

`shared/voxelRig.js` 把正面圖降到 90 格高（= `PIXEL_ART_GRID_HEIGHT`，像素風
一格剛好一顆體素），以輪廓切成頭、軀幹、雙手、雙腳六個部位，依「離輪廓多遠」
充氣出圓弧斷面的厚度；`public/screen/voxelCharacters.js` 建成 Three.js 網格，
手腳繞關節擺、軀幹微扭，朝向依速度連續轉。

- **不另疊一張 WebGL 畫布**。所有角色每幀先畫進一張離屏圖集，`drawCharacter`
  再逐一貼回 2D 角色畫布。另開一層的話名牌會被角色蓋住、Y 排序和箭頭的
  前後關係全亂，而且**合照只合成場景畫布 + 2D 畫布，會拍不到人**。
- **整體的左右擺動（wobble）只留給 2D 退路**。套在會擺手擺腳的體素角色上，
  就是現場回報的「人在抖」。
- **先找手臂、再只在手臂內側找胯下，且要有一道靠近中線的縫**。手掌常比
  手臂與身體的分界更往內伸，只數「分得出兩段」會把胯下判到腰上 —— 一條腿
  分到全部體素、另一條只剩幾顆，走起來是單腳跳。`test/voxel-rig.test.mjs` 有這個情境。
- **厚度是圓弧斷面，不是距離直接當厚度**。後者是菱形，側面看是一根棍子。
- **側壁用輪廓內側的顏色**。像素畫的輪廓是一圈墨線，直接沿用會讓手臂與身體
  的側面布滿深色紋；最外層的正面與背面仍是原圖。
- **光源強度乘 π**：Three.js r155 起是物理光照，不乘的話整體暗三成五。
- **每幀最多建一個模型**（一個約 50~100ms）。大螢幕中途重開、場上已有 30 人時，
  同一幀全建會凍住好幾秒；排隊中的人那幾幀先畫 2D。
- 拆不開的部位併在軀幹上（手臂貼身 → 只有腳動；長裙 → 腿很短），不會整個畫不出來。
- 開啟時若 WebGL 不能用、或骨架建不出來，該角色自動退回平面紙娃娃。

### CLIENT_SYNC / CLIENT_ROSTER：手機端個人視角

手機除了送搖桿輸入，也會收到自己的座標與半徑內的鄰居（相對座標），
供 `public/controller/avatarRenderer.js` 繪製個人視角畫布。

**兩個容易改壞的地方**，端對端測試都有回歸防護：

1. 推送必須放在主迴圈 `screens.size === 0` 早退**之前**。放在後面的話，
   大螢幕沒接上時所有手機畫面會整個凍結 —— 而「先開手機、投影機還沒接」
   正是佈場時最常見的狀態。
2. 節流比較要帶半個 tick 的容差（`>= CLIENT_SYNC_MS - TICK_MS / 2`）。
   主迴圈是 30Hz（33.3ms），若頻率不整除 tick，嚴格比較會讓某些格子
   差零點幾毫秒被擋下，實際頻率掉一整格（10Hz 曾因此實測只有 7.5Hz）。
   **選頻率時優先取能整除 30 的值**（15、10、6…），15Hz 實測抖動只有 ±1ms。

### 「找到自己」是這件作品的前提

參與者在手機上完成捏臉／生成後會抬頭找自己，而十個角色散在整個舞台
上並不好認。認不出來的話，「這是我」的連結就建立不起來 ——
而整件作品正是建立在那個連結上。

因此 `screen.js` 對新進場者標記 `arrivals`，在頭頂畫 6 秒的下指箭頭。

**首次收到名冊時刻意不標記**：大螢幕中途重開時場上可能已有十個人，
全部一起閃會變成一片光暈，反而誰都認不出。`rosterSeenOnce` 就為此存在，
`test/screen-arrivals.test.mjs` 有回歸防護。

### 操控狀態一律以伺服器的 α 為準

`#agency` 的提示曾用本地計時器（距上次推桿是否 < IDLE_THRESHOLD_MS）猜控制權。
但 `CLIENT_SYNC` 已經帶著伺服器仲裁的真實 α，本地計時器只該在
「尚未收到同步」時當備援。

兩者不一致最明顯的情境是**拍大合照**：伺服器鎖定場域收回控制權
（`mode: STAGED`），本地計時器卻仍顯示「你正在操控」——
使用者猛推搖桿沒反應，會以為自己的手機壞了。現在該模式下會明說
「正在拍大合照，請看大螢幕」。

### 操控延遲的組成

實測「推桿 → CLIENT_SYNC 回報速度改變」中位 **9 ms**（p95 21 ms）。
三個來源與各自的改善手段：

| 來源 | 原本 | 現在 | 手段 |
|---|---|---|---|
| 手機 20Hz 節流 | 平均 25 ms | ~0 ms | 按下的**第一幀立即送出**，不等計時器 |
| 伺服器 30Hz tick | 平均 17 ms | 不變 | 提高會等比增加所有廣播成本 |
| CLIENT_SYNC 週期 | 平均 50 ms | 33 ms | 10Hz → 15Hz |

第一幀立即送出只多了「每次觸碰一則封包」，連續推桿仍走節流，頻寬幾乎不變。
**不要為了再快而拿掉節流** —— 連續推桿時 nipplejs 的 move 事件遠密於 20Hz，
全部送出會讓現場無線網路吃不消。

α 爬升（`ALPHA_RAMP_UP_MS = 300`）不算在上表：它是刻意的「接手要柔和」設計，
不是延遲。調小會讓操控變得神經質，且與放手時的餘弦煞停不對稱。

名字走 `CLIENT_ROSTER`（只在成員變動時送）而不是塞進每個鄰居 ——
名字是靜態資料，隨 15Hz 的座標重送等於每秒多耗 25 KB 的重複字串。
這與「貼圖走 URL，不走 base64」是同一組取捨。

**第三個坑（已踩過）**：名冊的重送條件**不能**沿用 `stage.rosterDirty`。
那個旗標要等主迴圈的大螢幕區段才清除，而該段在 `screens.size === 0`
早退之後 —— 沒有大螢幕連線時它永遠是 true，名冊會變成 30Hz 廣播
（實測 2 秒送出 60 次）。改為比對名冊內容指紋，與大螢幕的清除時機脫鉤。
指紋要涵蓋名字而不只是人數，否則改名不會觸發重送。

這個故障端對端測試抓不到（`scripts/e2e.mjs` 全程接著大螢幕），
由 `test/client-roster.test.mjs` 直接對節流條件把關。

手機端**不自行模擬位置**，這與 issue #8（投影牆跑自己的 Boids）刻意相反：
本地模擬會讓使用者低頭看到自己穿牆、抬頭卻看見角色卡在牆邊。
伺服器狀態過期時收斂到靜止，不以最後速度外推（否則角色會飄出場外）。

### 上游一出狀況時：重試 429、熔斷器只算「上游掛了」（2026-10-15）

`scripts/gen-burst/`：假的生圖上游＋獨立一份生成服務（:5077），**不花錢**、不碰 :5055、
不寫帳本（`scripts/gen_load_test.py` 則是打真的 API、會花錢的那一支）。
上游健康時 3 人、8 人同時都會成功；問題在上游出狀況時這裡怎麼反應：

| 假上游 | main（10/15） | 改之後 |
|---|---|---|
| 一次只收 1 個，其餘回 429（3 人同時） | 1/3，失敗的人 0.5 秒就被打回（`RateLimitError`） | 3/3 |
| 每三次一次 502（5 人） | 4/5（`InternalServerError`） | 5/5 |
| 每次 48 秒，超過 SDK 的 45 秒 | 0/3（`APITimeoutError`） | 0/3（`upstream_timeout`，刻意不重試） |

`service.py` 的 `_imagegen_*`：

1. **429／5xx／連線錯誤自動重試**，間隔 2、4、8、10、10… 秒直到總預算用完，
   等待時**不佔**生成名額。逾時不重試 —— 那一次可能已經生完、已經收費。
   既有的「失敗不自動重生、要不要重生由驗證決定」（`test_paid_call_does_not_auto_retry_on_failure`）
   仍然成立：只重試上游在門口就拒絕、不收費的那幾種。
2. **熔斷器只算上游本身不能用**（逾時、5xx、連線、402）。429 不算 —— 一個人的三次重試
   就能讓全場熔斷；「模型回了文字沒回圖」也不算，那是這一張照片的問題。
3. SDK 的例外類別名換成穩定的碼（`upstream_rate_limited`／`upstream_timeout`…），手機各有文案。
4. 總預算 `_GENERATE_BUDGET_S`（預設 140 秒，2026-10-19 前是 130）必須小於互動層的 `GENERATE_TIMEOUT_MS`（150 秒，
   從送出才開始算，見 `server/generateQueue.js`）；剩下的時間不夠生一張就回 `queue_timeout`。

**還沒驗證的**：上游真正的同時上限是多少。實測前用真金鑰三支手機同時拍一次，
看帳本的 `error_code` 有沒有 `upstream_rate_limited`。

**測試不可以打到真的生圖 API**：開發機的 `.env` 有真金鑰，忘了替換
`generate_full_character_png` 的測試會真的生一張圖、真的付錢，測試照樣是綠的
（2026-10-13 發生過）。`backend/tests/conftest.py` 的 `no_paid_image_calls` 清掉金鑰；
`isolate_history` 把生成紀錄導到暫存目錄（原本只在 test_service.py，
`test_turnaround.py` 每跑一次仍往正式帳本寫兩筆）。

### 素體換裝：生圖 API 全掛時的退路（2026-10-18）

額度用完、上游掛掉時，拍照失敗頁多一個「自己換裝」：參與者挑髮型、上衣、外套、下身、
鞋子、配件與顏色，生成服務在本機組角色（`backend/dressup.py`，不呼叫任何外部 API）。
組出來的是與生成同規格的三視圖（1376×768），走同一條切圖存檔，所以會走路、會轉身、
進得了大合照，場上只有一種畫法。舊的捏臉 2026-10-18 拿掉了，換裝是唯一不靠生圖 API 的路。

- **部件怎麼來**：生圖模型在素體上「只加這一樣、塗成綠色」（`dressup/raw/`），
  對齊後跟素體比，變了的格子就是部件。綠的換成選的顏色；變成皮膚色的格子
  （裙子底下的腿）跟著膚色換。素體本身的髮、膚、T 恤、長褲、鞋依顏色分區
  （`layers/_base_labels.png`），眉毛眼珠只認「連到頭頂」的才算頭髮。
- **加造型不必改程式**：manifest 加一筆 → `scripts/dressup_generate.py` →
  看過 → `scripts/dressup_build.py`（步驟見 `dressup/README.md`）。新分類才要改 `dressup.py`。
- **換色的亮部只往白收 40%**（`HIGHLIGHT_LIFT`）：照原比例收，黑髮、黑裙的高光
  變成一條條灰白帶，看起來像褪色。
- 外套是獨立分類（`outer`）：連帽外套敞開穿在 T 恤外面，內外要能是兩種顏色。
- 預覽只組正面那一塊（`compose(box=...)`），約 0.24 秒；整套（三面＋存檔）約 2 秒。
- **臉（表情、眉毛、眼珠顏色）不走生圖**：五官只有幾格大，模型改不準，也不是「加一樣東西」。
  改用 manifest 的 `face` 段落：每個五官在三視圖上的固定位置（`slots`），表情、眉毛是手寫的
  格子圖（`stamp`，一個字一格，8px），先把那個五官抹成皮膚再畫。正面左右眼眉寫一次，右邊自動翻。
  臉比衣服髮型先畫：瀏海、帽沿、眼鏡會蓋在上面。
- **男生／女生兩個素體（2026-10-20）**：手機先選再換裝。女生素體（中長髮、短袖、長褲）的臉是
  **從男生素體逐格複製過去的**（`dressup.make_base`），表情、眉毛、眼珠才能共用；模型自己畫的臉
  總偏 3–5px，貼上去眼睛會歪。衣服髮型每個素體各畫一套（每套 17 張，約 US$1.2），
  manifest 的 `edit_note` 叫模型畫部件時保留長髮，否則畫後背包會順手把頭髮剪短。
- **長髮換馬尾會圍出一塊背景**：馬尾、脖子、背包把原本頭髮的位置圍住，去背只從圖邊清、
  走不到，側面會留一塊白三角。`compose(with_holes=True)` 回傳「素體的背景＋被擦掉的頭髮」，
  `split_turnaround(holes=)` 直接挖透明；不靠 `_enclosed_gaps` 猜（它整個略過側面）。
  同一個位置露出的上衣，有穿外套就補外套色——女生的外套原圖裡那塊被頭髮蓋著沒畫到。
- **換裝頁預覽要洗掉鄰居**：正面的框左右多留 48px，女生側面的馬尾會伸進來，
  `compose_front` 從正面右緣往右找第一條全白的縫，縫右邊洗白。
- **眼珠只認每隻眼最大的那一塊棕色**：眼角那一格陰影跟眼珠亮部同色（實測都是約 (88,48,32)），
  用顏色分不開，算進去的話藍眼的人眼角也發藍。
