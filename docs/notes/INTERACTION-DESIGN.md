# 互動玩法的設計判準

> 由 [CLAUDE.md](../../CLAUDE.md) 拆出。這裡是踩過的坑與當初的取捨理由 ——
> 動到相關程式碼之前先讀，多數條目都附了「不這樣做會怎樣」。

### 這件作品賣的不是場景，是「依場合配出來的互動」

市面上已經有大量虛擬場景產品（Gather、Zep 之類）。論場景數量、論美術、
論功能清單，這個專案都比不贏 —— 而且比那個方向本身就是走錯路，那是另一種產品。
真正的差異只有兩條，兩條都要守：

1. **參與者同處一室。** 那些產品解決的是「遠距的人要有個地方待著」；這件作品
   假設所有人就在同一個空間裡。大螢幕是公共資訊、手機是私人資訊，而通關要靠
   轉頭跟旁邊的人講話。「走到螢幕上那一圈裡才算完成」這種玩法在遠距產品裡
   沒有意義 —— 它的成立條件正是「大家在同一個房間」。
2. **玩法是依場合配出來的，不是內建的一張功能表。** 大學系上的新生訓練、
   企業部門的新人報到、研討會的茶敘 —— 人數、時間長度、彼此熟識的程度、
   主辦方真正想達成的事（混熟？分好組？認識跨部門的人？）都不一樣，
   該跑的玩法順序與該問的題目也就不一樣。

把一場活動需要的設定看成一份**配方**，現況是：

| 配方的欄位 | 現在存在哪裡 | 例 |
|---|---|---|
| 場景主題 | `shared/themes.js` 的 `id` | `kitchen` / `office` |
| 適用場合 | `shared/themes.js` 的 `occasion` | 「企業團建・新生訓練」 |
| 問卷題庫 | `shared/surveys.js` | 「負責煮／負責洗／負責吃」 |
| 玩法順序與參數 | `shared/recipes.js` 的範本（主辦端「節目單 → 從範本開始」） | 問卷 → 配對 → 賓果 → 尋寶 → 合照 |

最後一列原本**只在主辦端操作者的腦子裡**。2026-10-15 起寫成資料：每個場景至少一套
範本（加一套任何場景都能用的「快速破冰」），套進節目單後再自己增刪。範本的每一步與
「加入節目單」產生的格式完全相同，`test/recipes.test.mjs` 把題庫 id、任務時長、場景
歸屬逐一驗過 —— 範本壞掉不會報錯，要到現場按「下一項」才被伺服器拒絕。

還沒做的：範本只依場景挑，`occasion` 仍只是一行字；也還不能從現場的人數、時長自動推。

**這一條對程式碼的要求**（違反時不會報錯，只會讓專案慢慢退化成前面那類產品）：

- **任何新玩法都要可參數化，不能把某一個場景的語彙寫死在邏輯裡。**
  家具的顯示名稱只存在各場景的 `ITEMS`、由 `registry.propLabel()` 取用，
  就是這條規則既有的實作（見下面「轉場問卷」第 4 點）。伺服器端一旦出現
  「湯鍋」兩個字，那個玩法就只能在廚房跑。
- **評估新功能時問的不是「好不好玩」，而是「它讓這一場更好，還是讓配方的
  表達力更強」。** 後者優先 —— 前者只服務一次活動，後者服務每一次。
- **題庫要能整組換。** 新生訓練要問的（科系、住哪、想參加什麼社團）與企業部門
  報到要問的（部門、年資、擅長什麼）完全不同，而問卷的答案正是後續分組的依據。
  題庫寫死就等於場合寫死。

### 互動遊戲的判準：這個機制需不需要開口講話

這件作品要的不只是「參與者操控角色」，而是**操控角色的人彼此開始交流**。
因此新增任何玩法之前先問一句：**通關路徑上有沒有一步必須跟另一個人講話？**

沒有的話，再好玩都會讓現場更安靜。`server/pairing.js` 開頭那句註解
（「這個索取動作本身就是破冰」）就是整個判準的原型 —— 配對碼的作用
不是驗證，是把「搭訕」這個社交難題降級成「請問你的號碼幾號」這個任務難題。

**普通尋寶是反例，已經評估後否決。** 每個人都看得到冷熱提示的話，
從看提示到找到的每一步都不需要另一個人，而且找到後告訴別人對自己
是純損失 —— 它主動獎勵「不講話」。實際畫面會是十個人低頭各走各的。

#### 進場人格問卷：團隊分類的依據（`shared/persona.js`）

角色生成要等二十幾秒，這段時間順便答 3～5 題（預設 4 題），依 DISC 分成老虎、孔雀、
無尾熊、貓頭鷹四型，加上「沒有明顯偏向」的變色龍。結果記成 `persona` 標籤
（與轉場問卷的標籤同一處），主辦端名冊與「參與者」分頁的分佈都看得到。

- **判定規則只寫在 `shared/persona.js` 一處**：唯一最多、且至少 2 票才算那一型，
  否則是變色龍。手機當場揭曉與伺服器記下的標籤共用同一個函式，兩邊不會說法不一。
- **題目由主持人改，伺服器保存**（快照存「改過的題目」，沒改過就存 null，日後改版預設題目時才會跟上）。
  手機進場前還沒有 WebSocket，題目走 `GET /api/persona-quiz`；作答隨 `CLIENT_JOIN` 送出。
- **作答帶題目版本**：主持人在某人答題期間改了題目，舊答案對不上新題目，伺服器不判定
  （主辦端會看到「未作答」），而不是用錯的題目硬算出一個標籤。
- **不能略過**（2026-10-19 試玩回饋，原本一律可略過）：略過的人之後沒有機會再填，
  以進場類型為條件的任務、賓果格子、依類型分組都把他排除在外。只有 4 題，拍照路徑嵌在
  「生成中」那一頁，利用等待時間作答，角色先好了也會等問卷答完才換頁；換裝沒有等待，
  改在進場前跳出（Esc 也關不掉）。讀不到題目（伺服器剛重啟）時照樣不問、不擋進場。
- **一個角色答一次，不是一支手機答一次**：「重新進場」「換一個新角色」會清掉上一次的作答
  （`resetPersona`）。原本存在手機上就不再問，同一支手機的下一個角色換裝進場時沒有問卷、
  直接沿用上一個人的動物類型（2026-10-19 回報）。同一個角色重新整理、斷線接回不重問。
- 至少 3 題：題數太少時幾乎每個人都會是變色龍。

#### 私訊：刻意做成「開場」，不是聊天室（`server/messages.js`）

2026-10 應需求加入：在手機畫面上點別人的角色，傳一句文字給他。自由文字本身
**不滿足**上面的判準 —— 可以不轉頭就跟人交流。所以它被刻意限制成只適合「開場」：

- **最多 60 字、沒有對話串**：夠說「我在籃球架旁邊，要不要組隊」，不夠在手機上長聊。
  面板上的提示也是「約好了就走過去當面聊」。
- **只點得到手機畫面上看得到的人**（也就是在你附近的人），沒有全場名單 ——
  名單會讓人站在原地傳給遠處的人，完全不必移動。

**不要把它擴充成聊天室**（對話紀錄、群組、已讀、全場名單），那是把這件作品推回
Gather 那一類產品的最快路徑。

自由文字在陌生人、可能是學生的場合一定要有防護，四條缺一不可：

1. **封鎖**：之後的訊息靜默丟棄，寄件人仍看到「已送出」—— 告訴他被封鎖只會換來換個方式繼續。
   封鎖的人自己也不能傳給對方，點對方時面板只給「解除封鎖」（否則就成了我能傳你、你不能回我）。
   封鎖名單在伺服器，以 `MSG_BLOCKS` 在進場時補送給本人，手機重整也不會忘。
2. **檢舉**：只有收件人能檢舉那一則（否則任何人能拿 id 翻別人的私訊），進主辦端
   「參與者」分頁，主辦端可直接移除寄件人。檢舉清單在 `HOST_AUTH` 時補送。
3. **主辦端只看得到被檢舉的那幾則**，看不到一般私訊。投影模式下整塊隱藏。
4. **頻率限制**：兩則間隔 2 秒、每分鐘 10 則（`server/config.js` 的 `DIRECT_MESSAGES`）。

全部只在記憶體，不寫快照：伺服器重開，私訊與封鎖名單就沒了。這是單場活動的工具。

手機端的點擊要在**捕獲階段**先攔：畫布是 `pointer-events:none` 的背景，上面蓋著
static 模式的搖桿區，搖桿區裡任何一點按下去都會被 nipplejs 接走、角色朝那邊衝一下。
搖桿底座 85px 內不判定點人（想走路的手指落在角色上時，走路優先）。

#### 尋寶：先知模式（`server/treasure.js`）

改成資訊不對稱之後才成立：

| | 看得到冷熱 | 能得分 |
|---|---|---|
| 先知（一人） | ✅ | ❌ |
| 其他人 | ❌ | ✅ |

先知只能用喊的把隊伍導過去。講話從「可有可無」變成唯一的通關路徑，
而先知沒有藏私的誘因。**三個不能動的地方**（測試都有回歸防護）：

1. **`publicView()` 絕不能含座標。** 手機只要拿得到座標，開發者工具
   就能直接看到答案，而現場一定有人會這麼做。大螢幕與主辦端另外收到
   座標是刻意的 —— 它們是公開畫面，不在參與者手上。
   `scripts/e2e.mjs` 直接檢查手機收到的原始封包字串。
2. **先知踩上去不算找到，且得 0 分。** 先知一旦能得分，就有動機自己
   走過去而不是喊出來，整個設計就垮了。
3. **冷熱回報的是「最近的非先知角色」的距離**，不是先知自己的。
   回報他自己的距離會讓他本能地往寶藏走，而那對隊伍毫無幫助。

冷熱推播與踩中判定放在主迴圈的 `screens.size === 0` 早退**之前**，
理由與 CLIENT_SYNC 完全相同（投影機還沒接上時整場尋寶不能沒有反應）。
冷熱只在**等級變動**時推送，不是每幀 —— 先知要的是「變熱了」這個事件。

#### COLOR_HUNT：找特定顏色的人配對

驗證模型與 PAIRING 相同（雙方確認），只多一道顏色條件，因此
`server/index.js` 的 `PAIR_MISSION_TYPES` 把兩者一起放行。
它逼人抬頭看**真實的人**而不是看螢幕，正好破解「大家盯著手機」的問題；
而角色顏色本來就取樣自真實服裝，條件天然成立，不必另建資料。

**顏色判定的三個坑**：

1. **不能沿用調色盤白名單。** CV 角色的顏色取樣自真實照片，無法事先
   列舉（與 `avatars.js` 的 `HEX_RE` 是同一個理由），因此走 HSL 色相分族。
2. **無彩色必須在色相之前攔截。** 飽和度為 0 時 hue 恆為 0，
   純以色相判定會把白襯衫全判成紅色。
3. **飽和度門檻不能設太高。** 調色盤裡的鼠尾草綠 `#84A98C` 飽和度只有
   0.18，門檻設在 0.18 會讓它被判成「黑白灰」—— 而它在畫面上明顯是綠的。
   「看起來有顏色卻被判無彩色」是最難跟現場參與者解釋的失敗。現值 0.12。

顏色不符在**提交碼那一步就擋下**，不等對方確認：讓 A 白等 30 秒才被
告知「他不是紅色的」很差，而且會佔用雙方的 pending 名額。為此
`pairing.js` 多了唯讀的 `peekTarget()` —— 它**刻意不碰 `lastClaimAt`**，
否則顏色不符會白白吃掉冷卻，使用者馬上改找正確的人時會被擋下。

#### 以標籤為條件的任務：TRAIT_HUNT／DIFF_TRAIT／SAME_TRAIT（`server/missionRules.js`）

條件取自參與者身上的標籤（`server/traits.js`；轉場問卷移除後，目前只有進場人格會寫標籤）。
這些標籤**看不出來、只有本人知道**，所以比 COLOR_HUNT 更徹底地逼人開口：
「你是哪一型？」就是那一步。日後再加會寫標籤的玩法，這三種任務自動就能用新的標籤，不必改。

- **找某一類（TRAIT_HUNT）**：被輸入碼的那一方要是指定的類型，與 COLOR_HUNT 同方向。
- **找不同類（DIFF_TRAIT）**：跨出自己的小圈圈 —— 企業團建「認識別部門」、新生訓練「認識別系」。
- **找同類（SAME_TRAIT）**：分組前先讓同類的人找到彼此。

四個刻意的決定：

1. **主辦端只能從場上真的有的標籤挑**（`traitCatalog()`）。列出沒有人有的類型，
   等於讓主辦端發一個沒人做得完的任務。伺服器的 `buildRule()` 同樣拒絕不在場上的條件。
2. **同類／不同類要先告訴每個人「你是哪一類」**（`MISSION_ANNOUNCE.mine`）。參與者多半
   不記得自己進場時被分成什麼，不講的話他連該找誰都不知道。沒答過的人手機上直接寫
   「這個任務沒辦法參加」，而不是讓他一直被拒絕。
3. **配對失敗要說出對方是哪一類**（`PAIR_RESULT.peerLabel`）：「對方也是早鳥」比「不符合條件」
   好懂。這不是洩漏 —— 條件本來就是靠當面問的，對方自己會講。
4. **條件不符不記冷卻、查無此碼要記**，與 COLOR_HUNT 完全相同（見下方「顏色預檢不可成為
   枚舉管道」）。判定集中在 `pairRule()`，`handlePairClaim` 只有一條路徑。

**同時開好幾個任務時**（`missions.js`，最多 4 個）：一次配對只算進條件成立的那幾個，
其他照常。只有在**每一個**配對任務都帶條件、而且全部不成立時才在提交碼那一步擋下 ——
同時開著一般配對時它永遠成立，不擋人。「一樣的任務」看的是條件本身（`ruleKey()`）：
找貓頭鷹與找老虎可以同時開，兩個找貓頭鷹不行。集合任務每個集合點各自判定。

#### 湊人數集合：GATHER

N 個**還沒完成**的人同時站進集合點的圈裡、持續 2 秒才算，每人完成一次。

- **已完成的人不幫後來的人湊數。** 否則第一組到了之後，之後每個人走過去就自動完成，
  不必再找任何人。少了這條，這個任務只有第一組需要開口。
- **斷線中的角色不算人頭**：角色還在場上（`AGENT_TTL`），但那個人不在現場。
- 範圍是道具半徑 + `MISSION_TYPES.GATHER.reachRadius`（`shared/protocol.js`），大螢幕畫的那一圈
  與伺服器判定才會一致；集合點取自目前場景的 `spots`（號碼牌桌），沒有 spots 的場景發不出來。
- 不寫進社交圖譜：一群人站在一起不代表兩兩認識（同人物賓果的理由）。

#### 發布前檢查：現在發下去，做不做得完（`feasibility()`）

主辦端每改一次任務表單就問伺服器一次（`HOST_CHECK_MISSION`），表單下方即時顯示
「N 人中最多 M 人做得滿」與原因。發布與檢查走同一個 `checkMission()`，兩邊的判斷不會不同。

- **已配對過的兩人不能再配**（社交圖譜的 `ALREADY_PAIRED`）。連發幾個配對任務之後，
  可配的人會愈來愈少 —— 這是最容易被忽略的一種做不完，檢查有把它算進去。
- 每個人「還能跟誰配」是**上限**，不是保證：大家搶同一批人時實際完成的會更少。
- **沒有人做得完時預設擋下**，主辦端確認後（`force`）才放行 —— 人還沒到齊就想先把任務掛上去
  是正當的需求，硬擋只會讓主辦端繞路。

#### 尋寶會卡死的兩種情況（已由伺服器自己收拾）

賓客關掉分頁後角色仍留在場上 45 秒（`AGENT_TTL_MS`）才回收，
一場活動下來必然發生好幾次，因此下面兩種都不是假設：

| 情況 | 後果 |
|---|---|
| 先知離場 | 冷熱照算但沒有人收得到，其他人只能亂走 |
| 除了先知沒有別人 | 先知不能撿，沒有人結束得了 |

`treasure.viability()` 每幀檢查，不成立就自動中止並廣播原因。
**不能在主迴圈裡 `return`** —— 下面還有大螢幕的整段廣播，提早跳出會讓
投影畫面停一幀。用旗標往下讓它自然跳過。

還有兩處「補送」容易漏：中途進場與**斷線重連**走的是不同分支
（重連那段會提前 `return`），兩邊都要呼叫 `sendTreasureCatchUp()`。
先知重連時還要 `resendHeat()` 強制重送 —— 否則要等冷熱**等級變動**
才收得到，隊伍停在原地時可以是好幾十秒，而他正是所有人等著聽的那個人。

#### 顏色預檢不可成為枚舉管道

`peekTarget()` 刻意不含冷卻（顏色不符時不該罰正當使用者），
但呼叫端**必須自己把關**：4 位碼只有 10000 組，沒有冷卻就能在
幾毫秒內試完（實測 15ms）。若「顏色不符」直接 return 而不記冷卻，
攻擊者可從 `COLOR_MISMATCH` ↔ `NOT_FOUND` 的差異反推有效碼，
等於繞過 `claim()` 的整套防枚舉。規則是**只有真的顏色不符才免計冷卻**。

#### 大螢幕的寶箱要跟著透視縮放

`toScreen()` 是 3D 透視投影，但尺寸不能用 2D 的 `scale` ——
那會讓房間深處的寶箱畫得跟最前方一樣大，就是「貼紙浮在畫面上」。
要走 `roomScene.scaleAt()`，與角色的 `characterHeightAt()` 同一條路徑。

#### 中止尋寶不公布座標，找到才公布

`TREASURE_FOUND` 帶座標是對的（本輪真的結束了）；但 `TREASURE_ENDED`
**不能**用 `blastAll` 把座標送給手機 —— 沒有人找到，那個點就還是秘密，
主辦端可能馬上重開一輪（甚至同一個點），先講出來等於直接送答案。

這個洩漏是端對端測試抓到的（它檢查手機收到的原始封包字串裡有沒有座標），
而且**只在「本輪被中止」時才會發生**，正常玩完全看不出來。

#### 分區感知（`shared/scene.js` 的 `zoneAt`）

分區原本只是地板上的色塊 —— 伺服器完全不知道它們存在，走進暢飲區與
走到空地毫無差別。`zoneAt()` 讓「站到某個地方就會發生事」成立，而那是
展場裡最容易被觀眾自己發現的互動語言：不需要說明牌。

**只在換區時回報**，不是每幀：每幀回報的話 30Hz × 10 人是每秒 300 則
重複訊息，而現場的症狀只會是「網路很慢」，完全看不出跟分區有關。
推播同樣放在 `screens.size === 0` 早退**之前**（與 CLIENT_SYNC 同理）。

手機端的分區以 `CLIENT_SYNC` 的 `self.zone`（狀態）為準，而非只靠
`ZONE_SELF`（事件）—— 重連的人已經錯過了那則事件，只有狀態拿得到。
這與尋寶的 `sendTreasureCatchUp()` 是同一類補送問題。

#### CSS 類名撞名：主辦端的 .swatch 已經有人在用

`.swatch` 同時被三個地方使用：名冊縮圖（`avatarThumb`）、生成歷史縮圖
（`historyThumb`）、以及 COLOR_HUNT 的顏色選單。前兩者是既有的，
因此顏色選單改用 `.color-swatch`。

共用會讓名冊與歷史的縮圖被套上 flex 版面與 `::before` 色塊而變形 ——
**與控制器 `.bar` 撞名（頂端狀態列 vs 生成進度條）是同一類問題**，
那次的症狀是頭像／名字／積分／離開鍵被壓扁裁切。

這類 bug 不會有任何錯誤訊息，只會在某個頁面上默默壞掉。在共用的
樣式檔裡加通用類名之前，先 grep 一次那個名字。

#### 兩者的共用常數都在 shared/

`shared/colorFamily.js`（色族）與 `shared/heat.js`（冷熱等級 + 判定半徑）
被伺服器、大螢幕、手機三端共用，理由與 `EMOTE_GLYPH`、`QUIZ_CHOICES`
完全相同。特別是 `TREASURE_RADIUS`：伺服器據此判定「踩到了」、大螢幕
據此畫出光圈，兩邊各存一份會出現「畫面上明明踩進圈裡卻沒有反應」，
而參與者只會覺得系統壞了。`server/config.js` 直接再匯出，不另行定義。

### 轉場問卷（`server/survey.js`）

切換場景的空檔問一題沒有正解的題目，答案留成參與者身上的**標籤**，
供後續任務當條件使用（「答『負責煮』的人到湯鍋集合」）。

**為什麼不併進 `quiz.js`**：問答有兩條不可妥協的規則 —— 正解絕不離開伺服器、
一人一題只能答一次且不可更改（否則速度分失去意義）。問卷兩條都不適用。
塞進同一個狀態機，每個分支都得先問「這題算不算分」，
而算錯的那一次不會報錯，只會讓某個人莫名其妙多了 100 分。
判斷同 `missions.js` 開頭：驗證模型差異極大的東西不共用判定邏輯。

**四個刻意的決定**：

1. **標籤在作答當下就寫入，不等收題。** 標籤才是問卷的產物，題目只是取得它的手段。
   等收題才寫的話，主辦端忘記收題（現場很常見）就等於整題白問。
2. **問卷可以改答案**，與問答相反。沒有速度分，改了沒有人吃虧；
   而按錯卻不能改，那個人身上的標籤就會一直是錯的。
3. **標籤要進快照。** 它是「這個人是誰」，不是「這一題問到哪」。伺服器重開後
   參與者以原憑證接回同一個角色 id，標籤必須還在 ——
   否則以標籤為條件的任務會在重開後把所有人都判成不符合。
   進行中的那一題則刻意不還原（同 quiz：倒數已經沒有意義）。
4. **選項可以綁道具 id（`option.spot`）。** 「答這個選項的人到那個家具旁集合」
   因此有了單一事實來源：大螢幕畫的地點、主辦端顯示的名稱、伺服器判定的座標
   都指向同一個道具。名稱只存在各場景的 `ITEMS`，由 `registry.js` 的
   `propLabel()` 供三端取用 —— 在別處抄一份，換主題時就會出現
   「主辦端說湯鍋、大螢幕寫洗手台」而兩邊都不報錯。
   同一主題內**道具名稱不可重複**（`test/themes.test.mjs` 把關）：
   兩張桌子都叫「工作桌」時，「到工作桌集合」會指向兩個不同的地方。

**補送**：手機的中途進場與斷線重連是兩條不同分支（重連那條會提前 return），
兩邊都要呼叫 `sendSurveyCatchUp()`，而且要一併補送自己已經選過什麼 ——
否則重連回來的人會看到一個可以重按的空白題。大螢幕與主辦端在
`SCREEN_HELLO` / `HOST_AUTH` 時補送題目與分佈（同尋寶面板的前例）。

**手機不顯示全場分佈**，那是大螢幕的工作。手機是私人資訊、大螢幕是公共資訊，
這個分工是所有新玩法的共同前提。

### 問卷有兩種：按一下就結束的，與要走過去才算的

同一套問卷機制下有兩種題目，而它們在現場是完全不同的兩件事：

- **純手機題**（選項沒綁地點，例如「早鳥還是夜貓」）—— 低頭按一下就結束。
  它收得到資料，但全場沒有任何人站起來。
- **到場才算**（每個選項都綁了場景裡的道具）—— 按完還要走到大螢幕上那一圈
  裡才算完成。答案相同的人因此會在實體空間裡聚成一堆，而那正是整件作品要的：
  **讓螢幕上的選擇變成現場的站位**。

預設是後者：只要每個選項都綁了地點，`SurveySession.start()` 就自動要求到場
（主辦端可以取消勾選）。選項沒有全綁地點時這個要求會被忽略 —— 否則選到
沒地點那一項的人永遠到不了位，而畫面上只會看到那一欄的到位數停在 0。

**到位由伺服器的座標判定**，不是手機回報的。手機根本不知道自己在房間的哪裡
（它只有搖桿），也不該由它說了算。主迴圈每拍呼叫 `survey.syncArrivals()`，
只通知狀態真的變了的那幾支手機 —— 每拍廣播給全場是每秒九百則重複訊息。

### 集合範圍的半徑不能隨便取

`SURVEY.arriveRadius` 放在 `shared/surveys.js`，三端共用：伺服器據此判定、
大螢幕據此畫出地上那一圈、手機據此顯示到了沒。各寫一份會出現
「畫面上明明站在圈裡卻不算到位」——現場最惱人的一種故障，因為它看起來像
系統壞了而不是規則。

值是 45，由上限倒推：同一題的兩個集合點**圈圈不可以重疊**，否則站在中間的人
同時落在兩個答案的範圍裡。下限由站位決定：道具同時是障礙物，角色擠不進 r 以內，
實際站位大約在 r + 身體半徑，45 剛好容得下繞著一張桌子站一圈的人。

**但不重疊只是最低標。** 圈圈相切時兩群人仍舊肩並肩站成一片，大螢幕上看不出
是兩群還是一群，而「去跟答案一樣的人站在一起」正是這個玩法的全部意義。
題庫因此要求圈與圈至少隔 150（約三個人的身體寬度，投影出去看得出中間有條縫），
由 `test/survey.test.mjs` 把關。

這條規則逼著題目**重挑地點，而不是挑語意最貼的那一個**：廚房的洗手台就在湯鍋
正下方（相距 218，圈圈只隔 4），辦公室的會議桌緊鄰行動白板、3號工作桌緊鄰
1號工作桌 —— 原本四個圈擠成兩對。現在兩題的地點都散到房間四角，
最小間距 339 與 378。

另一條同樣不會報錯的坑：**集合點必須走得到**。角色被邊界力推回
`BOUNDARY_MARGIN` 以內，而道具座標是美術擺的；擺在邊界外的道具圈圈畫得出來
卻永遠沒有人進得去，現場看到的是「那一欄的到位數停在 0」，看不出原因。
也由測試把關。

### 整個 16:9 都要站得上人

房間那張圖是 2596×1460，而舞台原本是 1920×1080 —— 剛好只有室內地板那一塊。
量出來的結果：

| | 佔整張圖的比例 |
|---|---|
| 角色走得到的地板 | 54.7% |
| 再扣掉邊界回推帶（`BOUNDARY_MARGIN`）之後站得舒服的 | 34.6% |

左右各 338px 的菜園與露台（辦公室主題是大廳與遊戲間）、上方 270px 的牆與吊櫃、
下方 110px 的草地 —— **投影機有將近一半的畫素在演一個沒有人進得去的地方**。
而且浪費還不是最糟的：題目橫幅要讓位時，第一個被壓縮的就是房間
（見下面「大螢幕上，選項畫在它的地點旁」）。

**關鍵的那一個發現**：舞台到圖面的對應是**純平移**（圖面 x = 舞台 x + 338、
圖面 y = 舞台 y + 270），而且兩者都是 16:9。把舞台寬度從 1920 改成 2596、
水平位移歸零，x 就變成 1:1 —— **不需要任何縮放，角色一點都沒變小**，
只是多了 35% 的地可以站。可站立面積 54.7% → 74.0%。縱向維持原樣：
上面是牆與吊櫃、下面是樹籬，本來就不該站人。

代價有三個，都已經處理：

1. **所有道具座標 x 整體 +338**（`shared/scene.js`）。純平移，道具彼此的距離
   與集合點之間的間距完全不變，問卷那組間距測試一個字都不用改。
2. **牆從裝飾變成物理。** 以前走不到牆邊，所以牆不必擋；現在牆的兩側都站得了人，
   不擋就會看到角色穿牆進出菜園。`WALLS` 與 `DOORWAYS` 由同一份資料推導，
   美術直接讀 `DOORWAYS` 去挖那個洞 —— 分開寫的話，擋人的位置與畫出來的門會
   錯開，現場看到的是角色對著一扇畫出來的門撞牆。
3. **障礙從「圓」擴充成「線段 + 半徑」。** 用一排圓拼一道牆，角色沿牆滑行時會
   一格一格卡進圓與圓之間的凹處，而且一道牆要二十幾顆圓。幾何判定因此集中到
   `shared/scene.js` 的 `nearestOnObstacle()` —— 不只避障要用，**角色出生點
   （`state.js`）與寶藏落點（`treasure.js`）也要用**。它們原本都寫成
   `hypot(x - o.x, y - o.y)`，那個式子對線段量的是「到線段起點的距離」，
   寶藏會落在牆裡面，而症狀是這一輪尋寶永遠沒有人找得到，畫面上毫無異常。

測試守三件事（`test/scene.test.mjs`）：牆在門以外的地方真的擋得住、兩塊室外區
從室內走得到（網格 BFS）、門的淨寬容得下一個人。第二條守的是「牆改了但忘記留門」
—— 症狀是現場有一塊地永遠沒有人進得去，而那正是這次改動想解決的問題本身。

#### 室外的東西要有 id，不能只是背景

三畦菜（`grd_1` / `grd_2` / `grd_3`）已經從靜態背景搬進 `PROPS`，改由 `paintProp`
依座標畫。它們現在是真的障礙物，也能當集合點、顏色任務與任務目標 ——
與「1號桌」走的是同一套機制。主題只換外觀與名字（碰撞佈局在伺服器上，
不能因主題而異）：廚房是萵苣畦／番茄畦／紅蘿蔔畦，辦公室是兩間電話亭與一排置物櫃。
兩邊原本畫在背景裡的那幾樣東西要一併拿掉，否則同一個位置會有兩份家具。

**位置是倒推出來的，不是挑好看的地方擺。** 西側可站的範圍只有 0–293
（牆從 293 開始擋）：

| | |
|---|---|
| `x = 160`、`r = 54` | 道具佔掉 106–214 |
| 靠牆那條走道 | 79 |
| 靠圍籬那側 | 106 |

再往右擺，靠牆的走道會窄到角色擠不過去（光是道具的閃避緩衝帶就有 55）；
再往左擺就掉進 `BOUNDARY_MARGIN`（140）裡，變成「圈畫得出來但沒有人站得住」。
測試盯著這條走道，因為走道一旦被封死，症狀與當初沒有門一模一樣：
**那一塊地永遠沒有人進得去**，而畫面上完全看不出原因。

**還沒做的**：推車、長椅、花圃仍然只是背景，角色會從它們身上走過去。

### 採水果：籃子接力（`server/harvest.js`）

「走到菜畦旁邊按一下」是純個人動作，十個人會低頭各採各的，與被否決的普通尋寶
是同一個失敗。因此規則只有一條，但那一條逼出對話：

> **籃子只有一個，而且一個人一輪只能採一處。**

採完之後你手上的籃子對你已經沒有用了。要繼續只能交出去，而且得交給一個
**還沒採過**的人 —— 你得先知道誰還沒採（大螢幕上看得到），再把那個人叫過來。
「欸你過來，換你拿」就是通關路徑上那一步。三處採收點因此至少需要三個不同的人。

**沒有任何秘密，與尋寶相反。** 哪一處採過了、籃子在誰手上、誰已經採過，
三端送的是同一份狀態。藏起來並不會讓人講更多話，只會讓拿著籃子的人不知道要找誰；
真正逼出對話的是那條規則，不是資訊落差。

**五個刻意的決定**：

1. **交接由接的人發起，不是給的人。** 接的人要先被叫過去 —— 而「叫過去」正是
   這個玩法要的東西。給的人想主動脫手時用「放下籃子」，籃子留在原地讓人來撿。
2. **交接距離是 130，下限由 `BOIDS.separationRadius`（95）決定。** 分離力讓兩個
   自主漫遊的角色實際上擠不進 95 以內；設得比它小的話，「接過籃子」在沒有人
   操控的那一側永遠按不下去，而現場只會看到兩個人站在一起卻交不了東西。
   測試盯著這個不等式。
3. **採收是走到就算，不必再按一次。** 按鈕只留給「交接」那一個真正的社交動作，
   多一個鈕只會讓現場問「我到底要按哪個」。判定與問卷的到位共用同一套算法
   （半徑加在道具碰撞半徑之外）。
4. **籃子的位置每一拍都抄一份。** 拿著籃子的人關掉分頁後，角色要等
   `AGENT_TTL_MS`（45 秒）才回收，而回收的那一瞬間就再也問不到他在哪了。
   不先抄下來的話籃子會跟著人一起消失，這一輪永遠結束不了，
   畫面上完全看不出原因。現在人一離場，籃子就留在他最後站的地方讓別人去撿。
5. **出過力的人都算分，不是只有最後送回去的那一個。** 這是接力，
   只給最後一棒的話前面幾棒會覺得自己白跑。

**會卡死的那一種情況**（同尋寶，由伺服器自己收拾）：一人一畦的代價是
「還沒採的處數」可能多於「還沒採過的人數」，那時這一輪永遠不可能完成。
開局時就擋（人數少於處數直接拒絕），進行中由 `viability()` 每拍檢查並自動中止。

**伺服器端不可以出現「菜畦」兩個字。** 採收點與放回點都是 `shared/harvest.js` 裡的
道具 id；同一組 id 在廚房是菜畦與蔬果籃、在辦公室是電話亭與零食吧，
名稱由各場景的 `ITEMS` 決定（同轉場問卷的 `option.spot`）。寫死名稱就等於
把這個玩法鎖在廚房，而那正好違反前面那條場合適配。

#### 大螢幕是這個玩法唯一的公開資訊來源

手機上刻意不寫家具名稱（理由同問卷的到場題），因此三件事都得在大螢幕上講清楚：

| 要回答的問題 | 畫面上的東西 |
|---|---|
| 還有哪幾處沒採 | 每一處的名牌：`還沒採` / `✓ 採好了`，地上一圈虛線／實線 |
| 籃子在哪 | 持有者頭上的籃子記號；沒人拿著時畫在地上 |
| 我可以找誰接手 | **採過的人**頭上一個 ✓ |

最後一列是反過來標的：一輪下來採過的人永遠比較少，標他們比標「還沒採的人」
乾淨得多，而拿著籃子的人要找的正是**沒有記號的那些人**。

名牌會夾回畫面內，上方放不下時改掛在道具下面 —— 菜畦貼著畫面左緣，
名牌置中就會被裁掉半截，現場看到的是「蘿蔔畦」這種少一個字的名字，
而那正好是任務要喊的那個詞。

**現場會踩到的一件事**：菜園只能從牆上那道門進出，而門在北側。
直直朝菜畦走會撞牆，得先往上繞到門口。人看得到門，所以這是繞路而不是故障；
但 `/dev/` 匯入台的「前往」是直線自動轉向，**它過不了牆** ——
用匯入台試玩時要自己分段下指令，那不是玩法的 bug。

### 大螢幕上，選項畫在它的地點旁，不列在橫幅裡

選項全綁地點時，橫幅只剩一行題目，四個選項改成畫在場景裡各自的家具旁，
每個標記帶著「到位 / 作答」兩個數字，地上另外畫出判定範圍。
這同時解決三件事：橫幅高度從 387px 降到 111px（房間可用高度 60% → 87%）、
「我選這個要走去哪」直接答在畫面上、以及圈圈填滿的過程本身就是進度條。

**湊齊的圈圈換成實線並加上 ✓**，還缺人的維持虛線。數字要看清楚得盯著螢幕，
而一圈線的虛實在場地另一端也分得出來。圈線內側再描一圈半透明白線 ——
場景裡同時有深色木地板與淺色地毯，單一顏色的線在其中一種底色上一定會糊掉。

**答了但還沒走到的人，頭上標一個自己答案顏色的三角。** 「還差一個」只說得出
數字，說不出是誰；標出來之後旁邊的人會開口提醒他 —— 而「通關路徑上要有一步
必須跟另一個人講話」正是本專案對新玩法的判準。個人選了什麼因此會公開，
但這類題目本來就是走過去給全場看的，站進圈子的那一刻答案已經公開，
記號只是早幾秒。

手機端因此**不寫家具名稱**，而是叫人看大螢幕上同名的那個標記。家具的顯示名稱
只存在於大螢幕的場景設定裡（換主題會變），手機再存一份必然漂移；而這題本來
就要人抬頭找地方，指向螢幕比在手機上描述位置更有用。

### 揮手與乾杯：要對方回應才算數（`server/greetings.js`）

2026-10-14 前，三個表情鍵（🍻💗👋）按下去只是自己頭上冒個圖示：沒有對象、
沒有人回應、不改變任何事。用本檔的判準看它不及格 —— 按的人沒有理由轉頭看
旁邊的人，現場玩兩下就沒人按了。

- **揮手**對準身邊最近的在線者，對方手機跳出「某某在跟你揮手 ［👋 揮回去］」，
  8 秒內回揮才算打了招呼。提示條刻意**不做成覆蓋層**：回揮的人要能邊推搖桿
  邊抬頭找人。
- **乾杯**要身邊兩人 3 秒內都按。只有一個人按就落空，手機提示「找身邊的人一起按」
  —— 3 秒短到必須喊一聲「欸我們一起按」，那句話才是目的，所以不要把時限拉長。
- 身邊沒人時直接告訴他（`NOBODY`），不讓他乾等。
- **愛心**維持原樣（單向），還沒決定要不要拿掉。

幾個不明顯的決定：

- **成功不寫進社交圖譜。** 圖譜的邊是「經雙方確認的實體接觸」，配對碼保證
  兩人真的講過話；互相揮手薄得多，混進去會稀釋研究資料。大螢幕因此只畫
  一道暖色光束、不留常駐連線（配對是青綠色的常駐線）。
- **「身邊」= 240，小於手機視角半徑 `CLIENT_SYNC_RADIUS`（320）。**
  手機說「你向小明揮手了」，小明就一定在你的個人視角裡，否則找不到人。
- **尊重私訊的封鎖**（`server/messages.js`）。揮手邀請也會讓對方手機跳出我的名字，
  封鎖擋不住它的話封鎖就沒用。規則照私訊：對方封鎖了我，我照樣看到「已揮出」，
  但他收不到、也不可能湊成互相揮手；我封鎖了對方，揮手不會選到他；碰杯任一方
  封鎖就不算身邊的人。
- **替另一方補圖示（`applyAction(..., { force: true })`）不重設冷卻。**
  實測抓到過：A 被回揮後 0.3 秒按乾杯，因為補圖示時重設了 600ms 冷卻，
  那一下被當成連按吞掉，手機沒有任何反應。測試已釘住。

### 話題桌（`server/topics.js`）

兩人以上在號碼牌桌（`shared/themes.js` 的 `spots`，「1號桌」那種）旁停留 2 秒，在場的
每支手機跳出同一題聊天題，大螢幕也在桌邊顯示。這是場景道具第一次在「主辦端沒開活動」的
空檔也有作用 —— 原本道具只在問卷、尋寶、採收時才派得上用場。

- **一個人坐下什麼都不會發生。** 拿到同一題的人自然會轉頭問「那你呢？」，那一句才是目的。
- **桌子取自主題的 spots**，伺服器不寫死任何一張；換主題時位置與名稱跟著換。
- **題庫獨立**（`shared/topics.js`），不跟轉場問卷共用：問卷答案會變成標籤拿去分組，
  這裡只是聊天，沒有答案、不記錄、不計分。選題原則寫在該檔開頭（不碰隱私）。
- 同一組人 90 秒內不重發；有新的人加入（且同一張桌距上次 15 秒以上）才換題。
- **相鄰的桌子共用「同一組人」的冷卻**：office 的 1、2 號工作桌靠得很近，兩人可能同時在
  兩張桌的範圍內，只會拿到一題（e2e 曾因寫死桌號而誤判）。
- 問答、問卷、尋寶、採收進行中自動暫停：主辦端帶活動時，桌邊不該突然跳出題目搶注意力。
  任務（配對）與賓果不暫停。主辦端「場景與合照 → 場景互動」可整個關掉。

**2026-10-17 試玩回饋**：

- **只在辦公室開**（`THEMES` 的 `topicTables: true`）。廚房、體育館的號碼牌是集合點與器材站，
  走過去是為了任務，跳出聊天題只會打斷人。`spots` 照樣留給集合任務。
- **卡片點一下不再收起**。原本整張卡是按鈕，手機上搖桿、角色都靠得很近，一碰就不見、也叫不回來。
  現在只有「收起」鍵會收、25 秒後自動收；收起後留一顆「再看一次話題」（3 分鐘）——
  題目是要念給同桌的人聽的，收起來之後常常還要再看一次。

### 人物賓果（`server/bingo.js`）

每人一張 3×3 卡，每格「找一個〔條件〕的人」，輸入對方的配對碼才算。參考實體活動常見的
networking bingo，天生符合本檔的判準：每一格都要開口問人。

- **同一個人在一張卡上只能填一格**（`USED`）。少了這條，找到一個條件很多的人就能一口氣
  填好幾格 —— 玩法就從「認識很多人」退化成「找到一個萬用的人」。
- **條件全部取自既有資料**：衣服顏色（看得到但還是得過去要碼）、進場人格類型（只有本人
  知道，非問不可）、轉場問卷答案。所以先跑過進場問卷或一題轉場問卷，卡片才有變化；
  只有兩三人或沒人答過問卷時，卡上大多是補位的「找一個你還不認識的人」（用社交圖譜判定）。
- **只發場上除了自己以外至少有一人符合的條件**。怎麼找都找不到人的格子等於懲罰參與者。
  「場上」只算**連著線**的人（`bingoPresent`）：斷線、轉入漫遊的角色人不在現場，
  算進去就會出現找不到人的格子（2026-10-19）。
- **衣服顏色要取對**（2026-10-19 試玩，`backend/slicer.py` 的 `sample_fallback_colors`）：
  大頭 Q 版（約 2.2 頭身）的「上身」切片有將近一半是下巴與脖子，取中位數落在膚色上，
  白襯衫被判成「橘黃」。CUTS 是跨語言耦合、改了會動到渲染，所以修在取色：先取膚色
  （頭部「像皮膚的顏色」的眾數），衣服排除膚色後取最多的顏色。**只對之後生成的角色有效**——
  已經生成的角色，顏色存在手機與伺服器的角色資料裡，要重新生成或換裝才會更新。
- **暗色不算紅**（2026-10-19 試玩）：黑上衣在暖光下取樣成 #4D2A24（暗咖啡），色相落在紅色 ——
  全場沒人穿紅卻出了「衣服有紅色的人」。`shared/colorFamily.js` 現在把「暗（亮度 < 0.3）而且
  不鮮豔（飽和度 < 0.55）」的顏色歸黑白灰；酒紅、深藍這種暗但鮮豔的仍保留色族。顏色任務共用同一條規則。
- **防枚舉**：填格等於「這組碼的主人符不符合條件」的查詢。每一次嘗試都記配對的冷卻
  （`pairing.noteClaim`），不論成功失敗，見上方「顏色預檢不可成為枚舉管道」。
- **不寫進社交圖譜**：只有一方輸入碼，沒有對方確認（碼也可能是偷看的）。
- 被填進去的人會收到「某某把你填進了賓果」—— 那通常就是下一段對話的開頭。
- 卡片是私人的：大螢幕與主辦端只看得到進度前五名，看不到格子內容。
- **例外：開局勾的自我介紹**（2026-10-17 試玩回饋）。手機的賓果卡上寫著「你開局勾的：…」，
  主辦端賓果面板可以展開「每個人勾的自我介紹」。別人是照這個來找你的，勾完就忘會被問倒；
  主持人也要能在「他說他是、卻填不進去」時當場查。**大螢幕不送**（`bingoHostView` 只給主辦端）。

**2026-10-15 改版**：原本卡上實際只有兩種格子 —— 衣服顏色（看大螢幕就知道，對話只剩
「給我你的碼」）與進場人格類型，一張卡大約五格顏色加四格類型，玩兩次就膩了。

- **開局先問自我介紹**（`shared/bingoFacts.js`）。每人勾自己符合的幾句（最多 6 題），
  卡上就有「會一種樂器的人」這種只有本人知道的格子。要等答案回來才發卡，因為「場上至少
  有一人符合」才放進卡裡。只等**連著線**的人（`bingoAskers`）—— 斷線還留在場上的角色
  答不了，算進去就永遠等不到。發卡之後才進場的人直接拿卡、不再問。
  **不限時**（2026-10-19，原本 30 秒，試玩回饋太短；問卷下面也不寫備註）：在線的人都答完才發卡，
  有人一直不答時主持人按「不等了，直接發卡」（`HOST_BINGO_DEAL`）。
- **題庫依場景＋通用題**，主辦端可整份改（賓果面板「自我介紹題」，落地進快照）。
  一句話兩用：手機問「會游泳」、卡上寫「會游泳的人」，所以題目要寫成描述、不要寫成問句；
  多打的「的人」驗證時會收掉。**不碰隱私**（感情、宗教、政治、收入、健康、住址）——
  這些格子會被大聲問出來。
- **每類格子最多 3 格**（`KIND_CAP`）。不限的話有人拿到七格顏色、有人七格類型，同一輪難度差很多。
  挑不滿 9 格時才放寬，上限是為了平均，不是為了留空格。
- **人少時同一個人可以填不只一格**：上限 ceil(9 ÷ 其他人數)。原本 9 格要 9 個不同的人，
  不到 10 人時全卡永遠填不滿，主辦端卻看不出來。
- **稀有的格子可以重複找同一個人**（2026-10-19，`SCARCE_MATCHES = 2`）：場上（不算自己、只算在線的人）
  符合這格的人 ≤ 2 時，可以填已經在你卡上別格的人 —— 全場只有兩個人會樂器，他填過別格就永遠填不了這格。
  符合的人多的格子照舊擋下。兩條規則任一條成立就放行；「順便填」走同一套。
- **被找的人順便填**：A 輸入 B 的碼之後，若 A 也符合 B 卡上空著的一格，B 的手機出現
  「幫我填上」。不必再輸碼 —— A 剛當面拿過 B 的碼。邀請只發一次、不反過來再邀
  （否則兩人會無止境地互相邀請），90 秒後失效。收下時照一般填格的規則再驗一次。
- **配對碼 100 秒換一次，旁邊有倒數**（2026-10-19；原本 60 秒、沒有倒數，參與者不知道碼什麼時候會換）。
  伺服器送「還剩幾毫秒」（`PAIR_CODE.nextInMs`），手機的任務橫幅、配對面板、賓果卡都顯示「xx 秒後換新碼」。
  舊碼寬限期跟著拉到 100 秒。
- **手機版面**：本輪倒數寫在標題旁；自己的碼縮成一行放最上面，九宮格往上提；點了格子，輸入列黏在面板底部、
  輸入框跟配對的一樣大（原本輸入框沒套樣式、排在最下面要捲才看得到）。
  這讓賓果從「一方輸碼」變成兩個人都有進度，所以「今天遇見的人」那邊收下邀請的人也會記一筆。

### 配對碼的寬限與點到好幾個人（2026-10-17 試玩回饋）

- **「密碼對不上」**：配對碼每 60 秒輪換，舊碼原本只多留 15 秒。試玩時常見先記下對方的碼、
  走去找下一格的人、晚點才輸入，碰上輪換就變成查無此碼。寬限拉到 60 秒（`PAIRING.graceMs`，
  不能比輪換間隔長：只存一代舊碼）。新碼本來就避開仍在寬限內的舊碼，不會撞到別人。
  配對或賓果面板開著時碼剛好換了，手機會提示一聲。
- **點角色時點到旁邊的人**：遠處角色的點擊框被撐到至少 44px，三個人靠在一起時框會重疊，
  原本只取最上面那個。現在重疊時跳出「你要找哪一位？」讓使用者自己選（`pickAllAt`）。

### 2026-10-19 試玩回饋（第二輪）

- **操控卡住**有三個原因，各自修：
  1. 放手的那則封包掉了，角色照原方向一直走到 3 秒閒置逾時 → 推桿封包超過
     `INPUT_STALE_MS`（0.5 秒）沒來就當作放手。推桿中的手機每秒送 20 次，正常不會碰到。
     測試或工具若只送一次 `INPUT_MOVE` 就期待角色一直走，要改成持續重送（`/dev/` 已改）。
  2. 手指一按到別人的角色就打開訊息、搖桿推不動 → 改成放開時才判定點人（`pendingTap`）。
  3. 一小群人聚在一起時怎麼推都過不去 → 借過（`resolveAgentOverlap`）：
     撞上站著的人時對方往側邊讓、走的人保留部分速度擠過去。
- **進場問卷不能略過**（見上方進場問卷段落）。
- **賓果的衣服顏色看得到**：手機寫出「系統判定你的衣服」，顏色格子提示看大螢幕上的角色，
  填不進去時說出系統判定對方是什麼顏色。顏色看的是角色的上身與褲子，不是本人的衣服。
- **新活動整頁卡片**：任務、文字雲、賓果直接發卡時手機跳整頁卡片、大螢幕跳大字標題。
  同一活動只跳一次（手機記在 sessionStorage；大螢幕連上後 2 秒內的補送不跳）。
- **換裝快速套組**（女生 A–D、男生 A–B）與「生成完成頁可改用換裝」。
- **表情選單與角色動作**：揮手留在外面（它有互相揮手的判定），其他收進「表情」：
  10 個固定表情（不開放自由輸入：投影在全場面前擋不完不雅的字）與 3 個角色動作。
  動作沒有頭上圖示，由 `shared/character.js` 的 `motionPose` 以位移、旋轉、水平縮放做出來，
  不需要新的角色圖；用絕對時間算相位，大螢幕與手機不必同步起始時間。

### 解碼任務：一人拿符號、一人拿密碼本（`server/decode.js`，2026-10-21）

主辦端「任務類型 → 兩人解碼」。分組、出題、比對全在 `server/decode.js`（純邏輯，
`test/decode.test.mjs`）；伺服器接線在 `server/index.js` 的 `stepDecode`／`handleDecodeGuess`，
e2e 有一段「解碼任務」直接檢查三端的原始封包。

原型是 *Keep Talking and Nobody Explodes*：一個人看得到題目、另一個人拿著解法，
兩邊都只能用講的。這裡把它縮成一個手機上就玩得完的任務：

| | 手機上看得到 | 手機上看不到 |
|---|---|---|
| 符號手（A） | 一串符號，例如 🍎🔺🍎⭐ | 密碼本 |
| 密碼手（B） | 這一組的密碼本，例如 🍎＝3、🔺＝7、⭐＝1、🍋＝5… | 題目 |

A 念、B 查表報數字，兩人任一支手機輸入 `3731` 就解開。
**通關路徑上每一位數字都要講一次話**，而且雙方都不能自己做完 —— 這正是判準要的
（同先知模式：靠資訊不對稱，不是靠規則硬性要求）。

#### 規則

1. **搭檔由伺服器指定，但手機上不寫是誰，只寫顏色（2026-10-21 試玩回饋）。**
   全場分成兩個陣營：符號隊（大螢幕頭頂🔒）與密碼本隊（🔑），同一組同一個顏色。
   手機寫「你是符號隊・去找頭上也是紅色🔑的密碼本隊」——「你也是紅色的嗎？」就是第一句話。
   開始 `DECODE.revealAfterMs`（30 秒）還沒解開，才提示搭檔的名字，免得兩個人一直找不到。
   - 提示之前伺服器**連搭檔的 id 都不送**：手機有名冊，給 id 等於給名字。輸入錯誤時也不講是誰輸入的。
   - 顏色要念得出來、彼此分得開（`DECODE.keyColors`，十種），同時進行的組不撞色；用完才加號碼（紅 2）。
   - 分組優先排**還沒配對過**的人（社交圖譜）。不讓人自己挑，是因為自己挑的話大家只會找旁邊認識的人。
2. **每一組的密碼本都不一樣**（同一輪內隨機產生）。偷看隔壁組的密碼本沒用，
   只能問自己的搭檔。
3. **密碼本放干擾項。** 密碼本列 8 個符號，題目只用其中 3～4 個 ——
   不然 B 看到只有 4 個符號，就猜得到題目大概是什麼。
4. **人數是奇數時湊三人組**：A 拿符號，密碼本拆成兩半給 B、C（各 4 個符號）。
   每一位都得先問「這個在你那邊還是他那邊」，三個人都要講話，不會有人在旁邊閒著。
5. **解開後換人再來一組（一律如此，不是選項）**：解開的人跟其他也解開的人重新配對、交換角色
   （上一輪拿符號的，這一輪拿密碼本），一直到時間到。只解一組的話，
   先解完的人之後幾分鐘都沒事做；換搭檔則讓同一個任務裡認識更多人。
   剛合作過的兩人不會馬上被湊回一起：等不到別人超過 `DECODE.repeatAfterMs`（8 秒）才放寬。
   配對順序是「今天還不認識的」優先，其次是「上一組角色跟他相反的」，兩個人才都換得到角色。
6. **輸入錯誤**：只告訴你「對了幾碼」，不講是哪幾碼。連錯 3 次冷卻 10 秒 ——
   4 碼只有一萬種組合，不冷卻的話可以直接亂按。

#### 三個不能動的地方（要寫回歸測試）

1. **答案絕不送到任何一支手機。** A 只收到符號，B 只收到密碼本，比對只在伺服器做。
   e2e 直接檢查手機收到的原始封包字串，同尋寶的 `publicView()`。
   同一組的符號和密碼本**也不能同時送到同一支手機**，不然開發者工具一看就解開了。
2. **伺服器端不寫死任何符號或詞。** 符號集放在 `shared/themes.js` 每個場景的 `decodeSymbols`
   （廚房用蔬果、辦公室用文具），缺的話用一組通用的形狀（★▲●■◆♥）。
   寫死的話這個玩法就只能在一個場景跑（見本檔開頭的場合適配）。
3. **符號要念得出來。** 只用一眼就叫得出名字的東西（蘋果、三角形），不用長得很像的
   （兩種藍色、兩種杯子）。目的是讓人開口講話，不是考視力。

#### 會卡住的情況（伺服器自己收拾）

- **搭檔離場**：落單的人回到「等待配對」，下一次有人解開或有人落單時一起重配。
  斷線中的角色（`AGENT_TTL` 內）先等 15 秒再判離場 —— 手機鎖螢幕很常見。
- **中途進場的人**：先排進等待區，湊到 2 人就開一組。
- **場上只剩 1 個人可配**：手機寫「等其他組解完一起換搭檔」，不讓他乾等也不報錯。
- 開局人數少於 2：主辦端發布前檢查（`feasibility()`）直接擋下，同其他任務。

#### 畫面

- **手機**：上方是陣營與顏色（「你是符號隊・紅色」）和要去找誰，中間是自己那一半（符號或密碼本），下方是輸入框。
  兩支手機都有鍵盤，誰輸入都可以。
- **大螢幕**：每個人頭頂右上一顆圓牌（組色底＋🔒或🔑），解開時兩人之間一道光束。
  **不顯示任何符號或密碼本** —— 大螢幕是公開資訊，而這個玩法的資訊落差全在手機上。
- **主辦端**：設定碼長（3～6，預設 4）、每人目標次數（解開幾組算達標）、時長；
  發布後看得到「解開 N 組・M 組正在解・K 人等搭檔」。

#### 跟現有架構怎麼接

- 是 `missions.js` 的一種新任務類型 `DECODE`，可以跟其他任務同時開（最多 4 個），
  用同一套開場提示卡、計分（`missionFinish`，每解開一組各得一次）和節目單範本。
- 解開時記進「今天遇見的人」（`VIA.DECODE`，一起解碼），大合照的「依互動排位」也算得到。
  **不寫進配對的社交圖譜**：寫了之後這兩人就不能再用配對碼配對（`ALREADY_PAIRED`），
  解碼任務會悄悄吃掉後面配對任務的可配人數。
- 同時只能開一個解碼任務（碼長不進 `ruleKey`）：一個人同時在兩場解碼裡會拿到兩份符號，分不清是哪一組的。
- 之後的變化可以沿用同一個骨架，只換「解開的方式」：
  輸入數字（本版）→ 走到某件家具（拼半張圖），或密碼本某一格改成「去問穿紅衣的人他配對碼的第 1 碼」。

### 今天遇見的人與紀念卡（`server/encounters.js`）

手機上的「今天遇見了 N 個人」、名單面板與紀念卡都讀 `encounters` 這本帳，**不讀社交圖譜**。
2026-10-15 前名單直接讀圖譜，等於只有互輸配對碼的人才上得了紀念卡 —— 兩個人一起玩了賓果、
碰了杯、在桌邊聊了十分鐘，卡上卻沒有對方，玩家會覺得不公平。

- **圖譜維持嚴格，兩本分開。** 圖譜是研究資料，大螢幕連線、Boids 凝聚、賓果的「還不認識的人」
  都讀它；揮手、乾杯、同桌混進去會稀釋它（見上面揮手與賓果兩節）。不要為了紀念卡把互動寫進圖譜。
- **原則：兩個人都做了動作才算。** 配對、互相揮手、碰杯、交接籃子（從別人手上接過，
  從地上撿不算）、私訊（對方回過才算，單方面傳不算）、同桌聊天。
- **同桌不能拿發題當條件**：發題只要停留 2 秒，走過去站一下就有。改成兩人在同一張桌邊
  **一起**待滿 `sitMs`（60 秒）才算，逐對計時 —— 第三個人坐下不讓原本那兩人重新計時。
- **賓果只記在填格的那一方。** 輸碼的人確實去找過對方；被輸碼的人不該被塞進一個陌生名字。
  所以 A 的名單上有 B、B 的上面沒有 A 是正常的。被找的人收下「順便填」的邀請時，
  他也做了動作，他那邊也會記一筆。
- **尋寶不算**：先知對一群人喊話，被喊的人可能根本不知道先知是誰，名單上出現不認得的人
  會讓整張卡變得不可信。
- **封鎖雙向濾掉，而且是送出前才濾**（`sendSocialSelf` 的 `hidden`）。紀念卡會被分享出去，
  封鎖對象的名字和肖像不能出現在上面。帳本身不動，解除封鎖後名單自己回來。
  封鎖只在記憶體（`messages.js`），伺服器重開後封鎖消失，名單也會跟著回來。
- **排序由伺服器決定**：配對過的 → 有雙方動作的（種類多的在前）→ 只有單方面的；同層先遇到的在前。
  紀念卡取前 8 位，手機橫幅取前 6 位 —— 都是取前面，不是取最近的。
- **快照要存這本帳**；舊快照沒有時從圖譜補回配對過的人，活動中途升級伺服器名單不會清空。
- 顯示文字與順序在 `shared/encounters.js`。新增一種互動時：在那裡加一筆，在成功的地方呼叫
  `meetUp()`（或單方面的 `noteOneWay`），並先用本檔開頭的判準問一次「兩個人都做了動作嗎」。

### 大合照是另一條合成管線，記得所有參與過的人（2026-10-19）

**拍合照不影響大螢幕。** 原本是把場上的人定住、轉向鏡頭（依互動排位時還要走進隊形）
再截大螢幕，拍照那十幾秒全場動不了，而且只拍得到還在場的人。現在伺服器只決定「誰站哪」，
大螢幕在**看不見的畫布**上用同一套繪圖程式另外合成一張全員到齊的房間
（`public/screen/photoRender.js`；房間、靜止的道具、角色面向鏡頭、名牌），
場上的人照常走動，大螢幕畫面完全不變。生成服務只加標題與 QR。
沒有大螢幕或是 3D 主題時，Python 退回自畫舞台，照座標把每個人畫上去。

**不在場的參與者也站進合照裡**（`server/attendance.js`），不是另外列名單：
門檻是**操控過移動，或有社交連結**（配對、揮手、私訊、賓果……）—— 只掃了 QR、
進場就把手機放下的人不算。被主辦端請出場、換了新角色的舊角色不列。名單存在快照裡，
伺服器重開不會讓先走的人消失；身分目錄不能拿來用，主動離場時它就把人忘了。
原地拍時他們補進人群旁的空位（`photoLayout.js` 的 `guestSpots`）：並排左右至少 115，
不並排時前後至少差 175 —— 只差半個身位的話，後面那人的名牌被前面的人蓋掉（實拍過）。
依互動排位時一起排進隊形。場地塞滿、排不進去的人才不出現。
（中間試過「照片下緣疊一列不在場名單」，主持人否決：大家應該都在畫面裡。）

照片固定 1920×1080（16:9，與大螢幕同比例），標題列疊在最上面一條 —— 主持人決定維持比例
比完整露出房間重要。Python 收到不是 16:9 的底圖時等比縮放、補邊，不再硬拉。
**照片上不放 QR**：下載 QR 改在大螢幕右下角顯示（`SCREEN_PHOTO_QR`），拍完自動顯示，之後由主持人在
主控端側欄「合照 QR：顯示／隱藏」切換；排行榜開著時排到它左邊，疊在問答、文字雲的滿版面板**後面**；
大螢幕中途重開會補送。照片本身是紀念品，不該帶一塊條碼。主控端拍完會自動下載這張照片。

### 大合照的「依互動排位」（`server/photoLayout.js`）

> **2026-10-19 改版：不再排成一排一排的隊形，改成「錯落人群」。** 主持人看過好幾版後定下：
> 正中間是互動分數最高的人（跟全場熟悉度加總），之後每次挑「跟已經排好的人互動最多」的人
> 往外放，完全沒互動的人在最外圈（`orderCrowdByAffinity`）。站位是橢圓區裡的隨機點、
> 由內往外填；每個人的個人空間是基準（左右 135、前後 95）乘 0.75～1.35 的隨機倍率，
> 間距才不會固定；前面的人不蓋到後面那人的臉與名牌（`crowdSpots`、`CROWD`）。
> 試過的版本：方格候選（太整齊、看起來排隊）、固定間距（太規律）、間距太小（擁擠）。
> 角色與名牌大小跟 `public/screen/photoRender.js` 的畫法耦合，那邊改了 `CROWD` 要跟著改。
> 下面是舊隊形（`formationSlots`）的紀錄，函式與測試還在，合照不再用。

預設的合照是**原地拍**：大家站在哪就拍在哪，記錄的是現場自己走出來的樣子。
主辦端側欄「合照站位」可以改選**依互動排位**：排成一個面向鏡頭的隊形，今天越熟的人站越近。
兩種各有用處，所以是選項、不是取代。選擇記在主辦端那台電腦上（localStorage）。

- **熟悉度讀「今天遇見的人」，不讀社交圖譜**：圖譜只有配對，而同一對不能重複配對，
  每對最多一條邊，分不出誰比較熟。這本帳記的是互動**種類**（配對、揮手、同桌、私訊…），
  所以「越熟」= 兩人之間的互動種類越多。配對經雙方確認算兩種，賓果填格（單方面）算半種。
- **封鎖過的兩人熟悉度為 0**（雙向，同紀念卡），不會因為之前互動過被排在隔壁。
- **排法**：貪婪地把最熟的一對當起點，往頭尾接上最熟的人，接不下去就另起一串；
  誰都不認識的人排最後。隊形從後排起蛇行填位，所以順序上相鄰＝畫面上相鄰，
  換排時是上下相鄰而不是跳到另一頭。
- **隊形是一排一排的**（每排最多 12 人），左右間距 130、前後 105 —— 大螢幕上角色約
  170 高、100 寬，間距小於身寬就會疊在一起。人少時並肩站成一排。原本是「挑離中心最近的
  格子」，兩個人會剛好分到前後兩排、一個疊在另一個身後（2026-10-18 實拍）。
- **每排取最長的一段連續空位**，不讓桌子從中間切開一排；各排對齊同一個中心。
  辦公室的地板被家具切成好幾塊：20 人以內換排一律上下相鄰，24 人以上會有一兩處斷開。
- **站位避開道具與牆**；站位不夠時排不進去的人留在原地。
- **2026-10-19 起角色不再走進隊形**：隊形只用在另外合成的合照裡（見上一節），場上的人不動。
  下面兩條是當時「真的走過去」的紀錄；`stage.lockStage` 與 `arbiter.js` 的繞行還在、測試也還在，
  只是合照不再呼叫。
- **走過去要繞家具**：定位鎖定原本只有剛體修正（擋住但不繞），走遠路會卡在沙發前面
  直到合照逾時。現在離目標還遠時會切向繞行（`arbiter.js`），最後一段直走 ——
  目標貼著道具時還在繞的話，角色會在旁邊打轉到不了。原地拍的目標就是現在的位置，不受影響。
- 合照等待上限是 12 秒，時間到照樣拍。`test/photo-layout.test.mjs`
  驗證 16 人從場地另一角出發，12 秒時都已站到位置上（最後一段是減速接近，
  不一定剛好「算到位」，但離位置只差幾單位）。

**沒開大螢幕時的備用畫面**（`photo_composer.py` 的 `_layout_by_position`）：主控台裡的
預覽小窗不算大螢幕、不會被拿去截圖，只開預覽時合照會改由 Python 自己畫。這條路徑曾有兩個問題，
2026-10-18 一起修掉：場地寫死 1920 寬（實際 2596，人整體往右偏），以及人偶畫得比大螢幕大很多，
並肩的人疊成一團。現在由 Node 傳場地尺寸、只取有人站的那一塊來畫，站得近時整張人偶一起縮小。
主辦端收到 `fallback: true` 時會提示「先開好大螢幕再拍」。

### 用歷史角色試玩：`/dev/` 人物匯入台

「十個人同時在場時這個玩法成不成立」只能真的擺十個人上去看。但十個角色等於
十支手機、十張照片、十次約 25 秒的生成，開發時湊不出來。`public/dev/` 把
`public/assets/gen/` 底下過去生成過的角色列出來，一鍵放回場上，每個都有
方向鍵、社交動作、問卷／問答作答鈕，以及「前往某個道具」。

**每個傀儡都是一條真正的 WebSocket**，走完整的 `CLIENT_JOIN` → `INPUT_MOVE`
流程。伺服器上沒有任何「開發模式」分支 —— 一旦有，測到的就不是現場會跑的
那條路。`scripts/bots.mjs` 仍然保留：它用捏臉外觀、在 Node 裡跑，適合壓測
人數與頻寬；匯入台用真實的 CV 貼圖、在瀏覽器裡跑，適合看畫面與試玩法。

**色票要先離線取樣**（`python scripts/asset_colors.py`）。落地的只有四張
webp，`fallbackColors` 不在裡面，而顏色任務的色族判定讀的正是它
（`shared/colorFamily.js`）。不取樣就上場的角色會被補一組假色 ——
任務叫大家去找「紅衣服的人」，而那個人在畫面上是藍的。取樣跑的是
`backend/slicer.py` 的 `sample_fallback_colors` 本尊，不在前端用 canvas 另外
取一次：那等於把取樣邏輯在第二個語言再實作一次（同切片比例那條跨語言耦合）。

**已經用它量到的一件事**：十個人同時走到同一個道具旁時，角色會疊成一團，
名牌只剩最上面那一個看得懂。集合類任務（「答某個選項的人到 N號桌集合」）
因此不能只判「到了沒」就結束 —— 畫面上根本看不出誰到了。要嘛把人散佈到
道具周圍的一圈位置，要嘛集合點本身要給得比一張桌子大。

⚠ 匯入的角色佔用 `MAX_AGENTS` 名額，**現場請勿使用**（同 bots 的理由）。

### 掃描失敗一律降級，不擋人進場

相機權限被拒、非安全情境、照片不行 —— 停在失敗頁（重拍、從相簿選、自己換裝）；
生成本身掛了（額度用完、上游掛掉、排隊爆掉）—— 直接帶去素體換裝，照片量到的顏色當起點。

舊的 token 捏臉 2026-10-18 依使用者決定從手機拿掉了：場上只有一種畫法的角色。
代價是換裝要靠生成服務（Python）組角色，它沒開時手機只能請參與者通知工作人員 ——
所以生成服務一定要開著，開場前跑 `npm run doctor`。
