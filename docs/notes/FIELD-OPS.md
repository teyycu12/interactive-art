# 現場佈署：網路、憑證與裝置

> 由 [CLAUDE.md](../../CLAUDE.md) 拆出。這裡是踩過的坑與當初的取捨理由 ——
> 動到相關程式碼之前先讀，多數條目都附了「不這樣做會怎樣」。

### 生成的 25 秒幾乎全在生圖 API，不是本機算不動

實測一次完整生成的耗時分布（M2 筆電）：

| 階段 | 耗時 | 佔比 |
|---|---|---|
| 影像解碼 | 2 ms | — |
| MediaPipe 服裝/骨架 | 199 ms | 0.9% |
| MediaPipe 臉部 | 20 ms | 0.1% |
| Gemini 服裝語意 | 367 ms | 1.6% |
| Gemini 臉部語意 | 237 ms | 1.0% |
| **生圖 API** | **22,372 ms** | **96%** |
| 切片+存檔 | 84 ms | 0.4% |

**換更快的電腦不會有任何幫助** —— 96% 是在等 OpenRouter 的
`gemini-3-pro-image-preview` 回話。要縮短只有兩條路：換更快的模型，
或改變動線（讓人先用捏臉進場，生成好再換貼圖）。

併發已經處理過了：`service.py` 的 `ThreadPoolExecutor(max_workers=16)`，
每個請求佔 4 個 slot，因此約 4 人可同時生成而不互相排隊。

### 現場連線：手機必須與電腦同一個區網

`192.168.x.x` 是私有位址，手機用行動網路或別的 Wi-Fi 都連不到 ——
不是「連不上」，是那個位址在外面根本不存在。啟動訊息已經會提醒這件事。

校園網路的三個坑，都要**在展場那個實際房間**測過才算數：

1. **AP 隔離（Client Isolation）**：公用 Wi-Fi 常開此設定防止裝置互連。
   開了之後即使同一個 SSID，手機與筆電也完全看不到彼此。最惡毒的一個，
   因為「看起來明明同一個網路」。
2. **不同 SSID 走不同子網**：學生網與訪客網可能完全隔開。
3. **DHCP 讓 IP 亂跳**：見下一節。

要繞開全部三個，最省事的是**自備一台路由器**開自己的 Wi-Fi。
本專案的前端相依全部走 `node_modules`（見「前端相依一律由 node_modules 直出」），
因此區網不通外網也能完整運作。只有生成服務呼叫外部 API 時才需要上游網路。

### 大合照的 QR Code 也走同一個區網（2026-10-17）

沒設雲端圖床（`IMGBB_API_KEY` / `IMGUR_CLIENT_ID`）時，合照存進 `data/photos/`，
QR 指向 `https://<區網IP>:3000/photos/<id>.png`，同樣要同一個 Wi-Fi、第一次跳憑證警告。
原本 QR 寫的是 `http://127.0.0.1:5055/photos/...` —— 手機上的 127.0.0.1 是手機自己，
生成服務也沒有那條路由，**QR 掃得出來、網址打不開**，看起來像「QR 無法掃」。
電腦有好幾張網卡、QR 的 IP 不是場館那張時，啟動互動層前設環境變數 `PUBLIC_HOST`。

合照底圖是跟大螢幕要的截圖，伺服器挑**第一台連上的大螢幕**（主控台預覽除外）。
**現場只開一個 `/screen/`**：另一個開在背景的分頁若先連上，合照就是那個視窗的大小與
畫面。背景分頁的動畫會被瀏覽器暫停，截圖時改成整幀重畫，不再只有房間沒有人，但視窗
大小、構圖仍是那個分頁的。

### 憑證與 IP 綁死，DHCP 換號就失效

`scripts/make-cert.sh` 按「產生當下的 LAN IP」簽發憑證。而 IP 多半是 DHCP
配發的 —— 筆電重連 Wi-Fi 或隔天再開機就可能換號（本專案開發期間就實際發生過，
`.104` → `.111`）。

憑證一旦與實際位址不符，**服務照常啟動、位址看起來也正常**，
只有手機端會多跳一個「網域不符」錯誤，而那個訊息完全不提 IP。
現場只會看到「手機掃不進來」。

因此 `server/certcheck.js` 在啟動時比對憑證 SAN 與當下的 LAN IP，
不符就大聲警告。**只警告、不阻擋啟動** —— 憑證不符仍可使用（點過警告即可），
展演進行中「能跑但有警告」永遠優於「直接不給啟動」。

換過網路之後重跑 `bash scripts/make-cert.sh` 即可。

### navigator.vibrate 在 iOS 完全不支援

不是降級，是沒有。震動只能是加分項，不能是任何互動的唯一回饋 ——
每個震動點都另有畫面上的變化。腳步震動預設**關閉**並附開關：
走路時每秒約 2–3 次的持續震動，對電池與體感疲勞都有實際代價。
不支援的裝置上開關直接隱藏，而不是給一個按了沒反應的按鈕。


## 人數與延遲（2026-09-23 實測，上限由 10 提高到 30）

`MAX_AGENTS` 原本壓在 10，理由是 3D 客廳要為每個角色跑即時陰影與後製。
預設場景改為 2D 像素場景之後那項成本消失，於是提高到 30 —— 那也正是
`boids.js` 鄰居搜尋當初設定的目標值。提高之前先量過下列環節。

量測環境：開發筆電，30 隻壓測機器人（`node scripts/bots.mjs --count 30`），
辦公室主題。**現場投影電腦尚未量測**，實測前請至少重跑一次大螢幕那一項。

| 環節 | 30 人實測 | 判讀 |
|---|---|---|
| 模擬迴圈 | STAGE_SYNC 29.9 Hz（目標 30），幀距中位數 33.0ms、p95 48.9ms | 沒有掉速。Boids 的 O(n²) 在 30 人是每 tick 約 900 次距離計算，成本可忽略 |
| 大螢幕頻寬 | 每則 4.9 KB、143 KB/s（每台螢幕） | 區網無虞 |
| 手機頻寬 | CLIENT_SYNC 15.0 Hz、每則 756 bytes、11 KB/s（單支、視野內無人時） | 見下方「集合任務的頻寬陷阱」 |
| 大螢幕繪製 | 每幀約 6.0 ms（底圖＋21 個道具＋30 個角色與名牌），每多一人約 0.15 ms | 60 fps 的預算是 16.7ms，尚有餘裕 |
| 底圖繪製 | 約 84 ms，切換主題時一次性 | 只在建立場景時發生，不在每幀 |

### 40 人實測（2026-10-18，`MAX_AGENTS` 30 → 40）

開發環境（非投影電腦），39 隻 `scripts/bots.mjs` + 1 支量測手機 + 1 個大螢幕連線，20 秒：

| | 實測 |
|---|---|
| STAGE_SYNC | 30.0 Hz，間隔中位 33.3 ms、p99 38.2 ms；每則 6.4 KB、約 190 KB/s |
| 單支手機 | CLIENT_SYNC 15 Hz、約 28 KB/s（視野內最多 26 人） |
| 伺服器 | CPU 約 9%、RSS 約 78 MB |

生成排隊（假上游 6 秒、`GEN_MAX_CONCURRENT=4`、40 支手機同時送出，經 Node 排隊）：
40/40 成功，上游同時最多 4 個。排隊上限 `MAX_QUEUED_GENERATES` 同時由 40 提高到 60。
**投影電腦的繪製還沒量**，佈場時用 `--count 39` 看一次大螢幕畫格率。

### 真正的瓶頸是入場生成，不是互動層

`.env` 的 `GEN_MAX_CONCURRENT`（目前 4）決定同時送去生成的人數，
**Node 與 Python 讀同一個值**（`server/config.js`）。單人生成約 25–33 秒，
30 人同時掃描的話最後一位約等 30 ÷ 4 × 28 秒 ≈ **3.5 分鐘**。

超過上限的人在 Node 排隊（`server/generateQueue.js`，上限 60 人），先來先到；
手機每 2 秒查一次排第幾，顯示「前面還有 N 人」，輪到才開始跑進度條。
150 秒的生成逾時從輪到時才開始算。（2026-10-14 前是直接回 too_busy，
第 5 個人起要靠狂按重拍搶位子。）

**等待中斷線，結果用號碼牌領回**（`server/generateResults.js`）。等好幾分鐘時，
切去別的 App、點開通知、螢幕鎖定，iOS 都會砍掉生成請求的連線，但那張圖
照樣生完、照樣收費。原本手機只會顯示「生成服務連不上」，對方重拍就要再付一次錢。現在：

- 每次的結果（成功、失敗都算）依號碼牌留 5 分鐘，`/api/generate/status` 回
  `state: 'done'`，手機再到 `/api/generate/result` 領，領過就刪
- 排隊中斷線先不讓位：45 秒內手機還在輪詢就保留位子。輪到時連線已斷、
  又超過 30 秒沒輪詢的，直接跳過不送（還沒花錢）
- 手機的 fetch 失敗就改用號碼牌等；fetch 掛著不回、但輪詢已經看到 done
  的話，4 秒後也改用號碼牌領
- 切出去太久、位子已經讓出去的人，看到「離開畫面太久……再拍一次」

不這樣做的話：40 人場次最後幾位要等 4–5 分鐘，這段時間切出去看手機很常見，
每一次都是一張白付的圖，外加一次重新排隊。

30 人場次的處置（依成本排序）：

1. **分批入場**：主辦引導每次 6–8 人掃描，其餘先用捏臉進場（捏臉是刻意保留的備援路徑）
2. 調高 `GEN_MAX_CONCURRENT`：**先用 `scripts/gen_load_test.py` 壓測**（會花錢）。
   OpenRouter 對付費模型沒有公開的並發上限，但餘額低時有「進行中花費預算」，
   超過回 402 —— 餘額越低能同時跑的越少，加值後再壓測
3. 長時間排隊（> 1 分鐘）在真手機上還沒驗證過：iOS Safari、ngrok 對掛著不回的
   請求是否有自己的逾時，要實測。就算連線被砍，結果也能用號碼牌領回（見上），
   但「切出去再回來就自動接上」仍要用真的 iPhone 走一次

### 經 ngrok 時限流會變成全場共用

ngrok 轉發進來的連線 `remoteAddress` 全是 127.0.0.1。生成限流是每個來源
3 次 / 90 秒，共用之後就是**全場 90 秒內只能生成 3 次**。`server/clientIp.js`
在連線來自本機時改採 `X-Forwarded-For`；區網直連不採信，避免手機自己塞標頭
繞過限流。換別的反向代理前先確認它會帶這個標頭。

**取最右一段，不是最左邊。** 代理只會往後接，最左邊是客戶端自己送的 ——
採信它的話，每次請求換一個假值就拿到新的額度，一支手機能塞滿整個生成排隊。
多一層代理（例如 ngrok 前面再架一層）時，最右邊會變成那一層的位址，要跟著改。

### 集合任務的頻寬陷阱

CLIENT_SYNC 只送視野半徑（`CLIENT_SYNC_RADIUS` = 320）內的鄰居，所以單支手機
平時只有 11 KB/s。但**集合類玩法的本質就是把所有人聚到同一個點**，
那時每支手機的鄰居陣列會從 0 筆變成接近 29 筆。

以 STAGE_SYNC 實測的每角色約 163 bytes 估算，最壞情況單支手機約 5.5 KB × 15 Hz
≈ 80 KB/s，30 支合計約 2.4 MB/s。這是估算值、尚未實測，但方向明確：
**頻寬的尖峰會剛好落在任務完成的那一刻**，而那也是最不能卡的時候。

實測（2026-10-15，`scripts/bots.mjs --count 29` + 1 支量測手機，30 人隨機散布、未集合）：

| | 實測 |
|---|---|
| 單支手機 | 約 21.5 KB/s（CLIENT_SYNC 18.5 + 名冊 3） |
| 大螢幕 | 約 150 KB/s（STAGE_SYNC 每幀約 5.1 KB × 30 Hz） |
| 伺服器 | CPU 8–17%、RSS 約 50 MB；STAGE_SYNC 間隔 p99 38.6 ms |

散布時比上面的最壞估算低很多，**但這不是集合時的數字**。

**集合時實測**（2026-10-18，開發筆電，`bots.mjs --count 39 --gather` + 1 支量測手機
站在人群裡 + 1 個大螢幕連線，20 秒）：

| | 散開 | 集合 |
|---|---|---|
| 單支手機鄰居數 | 平均 2.2、最多 5 | 平均 32.5、最多 37 |
| 單支手機 | 5.8 KB/s（CLIENT_SYNC 每則約 395 bytes） | **48.9 KB/s**（每則約 3.3 KB，一個鄰居約 100 bytes） |
| 40 支合計 | 約 0.23 MB/s | **約 1.9 MB/s（≈ 16 Mbps）** |
| 大螢幕 | 約 204 KB/s，STAGE_SYNC p99 43.7 ms | 約 201 KB/s，p99 47.4 ms（集合不影響大螢幕） |
| 伺服器 | CPU 10–13% | CPU 12–16% |

比當初估的 80 KB/s 低，伺服器也撐得住。16 Mbps 對**自備的 5 GHz 路由器**沒有問題，
真正的風險在擠的校園 Wi-Fi：40 支手機每秒共 600 則小封包，比總頻寬更吃空中時間。

**試過但沒開：WebSocket 壓縮（permessage-deflate）**。`server/index.js` 的
`new WebSocketServer` 加 `perMessageDeflate: { threshold: 512 }` 一行就能開，同樣的集合情境：

| | 不壓縮 | 壓縮 |
|---|---|---|
| 單支手機（實際傳輸） | 47.8 KB/s | **5.9 KB/s**（約 1/8） |
| 大螢幕（實際傳輸） | 202 KB/s | **19.6 KB/s**（約 1/10） |
| 伺服器 CPU | 10–23% | 21–42% |
| 伺服器 RSS | 約 59 MB | 約 76–99 MB |
| STAGE_SYNC p99 | 46.0 ms | **72.5 ms** |

頻寬省很多，但伺服器每秒要壓約 630 則訊息，大螢幕的畫格間隔變得比較不穩（p99 超過兩幀）。
這組數字是機器人和伺服器跑在同一台筆電上量的，CPU 互搶，現場可能好一些。
2026-10-19 實測前不開：現在的頻寬在自備路由器上夠用，臨時換傳輸層反而多一個變數。
真的要開的話，大螢幕通常和伺服器在同一台或有線，可以讓 STAGE_SYNC 用
`ws.send(data, { compress: false })` 不壓，只壓手機的 CLIENT_SYNC，CPU 會省不少（還沒量）。

另外兩條路也還沒做：鄰居數設上限（只送最近的 N 個，但手機畫面上的人會突然消失），
或人擠在一起時降低 CLIENT_SYNC 頻率。

### 45 秒的離場延遲會吃掉名額

關掉分頁的角色仍佔用名額直到 `AGENT_TTL_MS`（45 秒）到期。壓測時實際踩到：
30 隻機器人結束後立刻再開 25 隻，全部被「現場人數已滿」擋下。

因此 30 的上限在現場等於「30 個同時在場的人，加上最近 45 秒內離開的人」。
若場次人數接近 30 且有輪替，要嘛調高上限，要嘛縮短 TTL —— 但縮短 TTL 會
讓斷線重連的人拿不回原本的角色，那是當初把它設成 45 秒的理由。

### 生圖 API 全掛時：素體換裝（2026-10-18）

拍照失敗頁的「自己換裝」不需要外部 API，只要生成服務還在跑。額度用完、上游掛掉時，
現場請參與者改按這個，而不是一直重拍；角色跟生成的同一種，大螢幕上看不出差別。
生成服務本身掛了的話這個按鈕不會出現，只剩「改用捏臉」。

### 主模型掛掉時的備援模型（2026-10-18）

主模型（Nano Banana 2）上游 5xx、連不上、重試到最後還是 429，或它的熔斷器已經跳開時，
生成服務自動改用前一代 Nano Banana（`google/gemini-2.5-flash-image`，每張約 US$0.04）。
它的三視圖切得出來，但髮色會飄、偶爾多畫一個照片裡沒有的包，所以**非不得已不用**：

- 逾時**不換**：那一次主模型可能已經生完、已經收錢，換了等於付兩次。主模型真的卡死時，
  連三個逾時熔斷器就跳開，之後的人直接走備援
- 額度用完**不換**：兩個模型扣同一個 OpenRouter 餘額
- 模型回了文字沒回圖、驗證沒過**不換**：那是那一張照片的問題
- 一直 429 時主模型先照常重試，生成總預算剩 60 秒時才換

用了備援的那一筆，`/generate` 回應帶 `backupModel`，生成紀錄的模型欄位也是它。事後畫風有落差，
先查這個。模型名寫在 `config.py`，各台電腦的 `.env` 都**不要設** `BACKUP_IMAGE_MODEL`
（`npm run doctor` 會抓）；要關掉就設成 `off`。
Nano Banana 2.1 當時上游共用額度天天滿、每次都 429，當備援等於沒有，所以沒選它。

實測（2026-10-18，同一張學士服照片，主模型故意擋掉）：主模型連三次 500、熔斷器跳開後
改走備援，22 秒、US$0.04，三視圖切得出來、去背乾淨。但**黑髮畫成棕髮、學士服底下的
牛仔裙變成黑褲**，而且**第三個人畫成朝左的側臉，不是背面**。最後這個現在會自動丟掉
（`turnaround.back_shows_face`：背面頭那段的膚色超過 5.5% 就不要），大螢幕往上走時
退回正面，不會一張側臉倒退走。髮色、衣服細節的落差沒有修，這就是「非不得已」的代價。

### 額度用完時手機曾寫「過載」（2026-10-14）

OpenRouter 對「輸出圖片」的請求要求**餘額至少 1 美元**，不足時在門口就回 402，
不扣錢、也不會因為重試而成功。當天儲值 20 美元、用到剩 0.78 美元時，生成全部
在 1 秒內失敗，手機卻寫「生成服務暫時過載」—— 熔斷器把 `garment_gen` 回報的
`insufficient_credits` 換成了 fallback 的 `circuit_open`，生成紀錄也只記 `circuit_open`。

現在失敗時回傳那次呼叫自己的錯誤碼（`circuit_breaker.CallFailed`），熔斷中的
快速失敗也會說出原因（`service._open_fallback`），手機顯示「生成額度用完了，
請通知工作人員」。**佈場前查一次餘額**：額度剩不到 1 美元時，生成一張都做不出來。
儲值後不必重啟，熔斷器約 20 秒後會自動再試。

## 事件紀錄（實測數據）

`data/state.json` 只有「最新狀態」，答不出停留時間、操控時間、斷線次數。
這些靠 `server/eventlog.js` 逐筆寫出的 JSONL：一行一筆、只附加不修改，
當機也只少最後一行，Excel / Python / JASP 都能直接讀。

**啟動時一定要帶場次名稱**：`PIXELAIR_SESSION=live-1019 bash start.sh`。
沒帶就是 `dev`，正式場次的資料會跟工程師測試寫進同一個 `data/events/dev.jsonl`
—— 而事後要從一份檔案裡挑出哪些是測試，幾乎不可能。檔名就是場次名稱，
`live` 開頭的在 `session_start` 標為 `kind: "live"`，其餘（含彩排）一律 `test`。
同一個名稱也寫進生成服務 SQLite 的 `experiment_id`。

| 事件 | 主要欄位 | 算得出 |
|---|---|---|
| `session_start` / `session_end` | kind、theme、resumed／reason（shutdown、crash） | 場次邊界 |
| `join` | agent、name、entry（photo／scan_fallback／builder）、genReq、rejoin（new／reattach／claim） | 入場時間、生成成功率、入場漏斗 |
| `disconnect`、`leave` | leave.reason：self／kick／timeout | 停留時間、斷線次數 |
| `mode_change` | from、to（SWARM／ACTIVE／STAGED） | 操控時間比例 |
| `pair_claim`、`pair_confirm` | agent（發起方）、peer、ok、reason、mission | 配對成功率、失敗原因 |
| `mission_publish` / `_progress` / `_complete` / `_close` | mission、type、target、count、by | 完成率、完成所需時間 |
| `quiz_start` / `_answer` / `_reveal` / `_end` | correctIndex、choice、elapsedMs | 作答率、答對率、反應時間 |
| `treasure_start` / `_found` / `_stop` | prophet、x／y、ms | 尋寶花費時間 |
| `harvest_start` / `_take` / `_drop` / `_done` / `_stop` | helpers | 接力參與人數 |
| `survey_start` / `_answer` / `_close` | key、choice、label | 轉場問卷作答率 |
| `photo_start`、`photo` | count、arrange（stay／affinity）、ok、uploaded | 合照參與人數、用了哪種站位 |
| `theme_change` | theme | 不同主題下的互動量 |
| `persona` | agent、type | 進場人格問卷的分佈 |
| `greet_invite`、`greet` | kind（WAVE／CHEERS）、agent、peer | 「要對方回應才算數」的互動次數 |
| `bingo_start` / `_claim` / `_end` | peer、cell、ok、reason、newLines | 賓果找人成功率、連線數 |
| `topic_card` | spot、agents、question | 話題桌被觸發幾次、誰跟誰坐下 |
| `message`、`message_report` | agent、peer、delivered（**不記內容**） | 私訊量、檢舉 |
| `waitlist_join`；`join.fromWaitlist` | name、position | 人滿時的候補長度、候補後有沒有進場 |

幾個不明顯的地方：

- **`genReq` 不是手機回報的**：生成服務用同一個 id 當帳本主鍵與貼圖目錄名
  （`/assets/gen/<id>/head.webp`），伺服器從貼圖路徑就取得到，拿它對
  `generation_runs.request_id` 就能查風格、耗時與重試。
- **「拍照失敗改捏臉」只有手機知道**：在伺服器眼中它跟直接捏臉長得一樣，
  所以手機在 `CLIENT_JOIN` 帶 `entry`。CV 角色一律記 `photo`，不採信手機。
- **關機時的那串 `disconnect` 不是參與者斷線**：`session_end` 先寫，
  之後 terminate 連線才觸發 close。分析時以 `session_end` 為界。
- **不記 `INPUT_MOVE`**：30 人一小時是數十萬筆，操控時間由 `mode_change` 就算得出來。
- **只存暱稱與 agentId，不存照片與重連憑證**（e2e 有檢查）。報告引用時以編號取代暱稱。
- 寫入失敗只警告一次並停用，**不拋錯** —— 為了紀錄讓現場的伺服器當掉是本末倒置。
- `PIXELAIR_PERSIST=0` 會一併關掉事件紀錄；e2e 用 `PIXELAIR_EVENTS_DIR` 寫到暫存目錄。
